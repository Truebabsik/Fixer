## Что сделать

Перевести окна решений из кода в данные: ядро должно **читать триггеры, варианты и эффекты** из
`Mission.data["windows"]`, а не из `WindowScript.locked_door` и не из зашитых правил.

**При этом наблюдаемое поведение на фикстуре обязано остаться прежним** — все 423 проверки зелёные,
ожидания тестов не правятся. Если приходится править ожидание — остановись и напиши в отчёте: это признак
изменения поведения, а задача не про это.

### 1. Триггеры (какие окна возможны)

`_maybe_open_window` (`game/sim/sim.gd:342-359`) сейчас жёстко ищет запертое ребро перед агентом.
Перепиши так, чтобы окно выбиралось по `trigger.type` из данных:

| `type` | Поля | Когда открывается |
|---|---|---|
| `locked_edge` | `edge` | группа стоит перед запертым ребром (текущее поведение — сохранить дословно) |
| `node_entered` | `node` | группа вошла в помещение |
| `guard_in_sensor` | `sensor` | охрана вошла в зону сенсора |

Порядок обхода — детерминированный (свои в порядке `own`, окна в порядке массива). **Одно окно срабатывает
один раз за миссию**: добавь учёт сработавших (например, множество id) и **не открывай окно на ребро, на
которое окно уже срабатывало**. Это требование из `02-format.md` §4.2 («одно окно — один срабатывающий раз»)
и закрывает находку исполнителя задачи 4: сейчас при запертом ребре окно открывается заново каждый шаг.

Для `node_entered` «вошла в помещение» = в этом шаге был `agent_moved` в этот узел. Для `guard_in_sensor` —
в этом шаге был `sensor_contact` по этому сенсору. Если у тебя возникнет соблазн срабатывать на «находится
в узле давно» — так нельзя: окно открывалось бы на каждом шаге.

### 2. Рантайм-форма окна

Составной id окна **остаётся** тем же, что сейчас: `"locked_door:%s" % edge_id` для окна с триггером
`locked_edge`. Это ключ событий (`window_opened`, `order_issued`, `order_silenced`, `order_refused`) —
менять его нельзя, на него смотрят тесты и презентация. Для новых триггеров собери id по той же логике:
`"<kind-без-_edge>:%s"` — например `node_entered:<node>`, `guard_in_sensor:<sensor>`; в событиях поле
`kind` должно нести вид окна (`locked_door` для запертого ребра — как сейчас).

Рантайм-список вариантов собирается из `options` **плюс** ветка молчания с id `silence` (`WindowScript.SILENCE`).
Сейчас `WindowScript.locked_door` кладёт `Silence` третьим элементом `options`; сохрани это: `order("silence")`
и `WindowScript.has_silence` обязаны работать как прежде.

### 3. Эффекты

Введи **один** применятель эффектов — сейчас `_apply_option` и `_apply_silence` знают про `unlock` и задержку
порознь (`sim.gd:424-449`). Он принимает эффект из данных:

| `type` | Поля | Что делает |
|---|---|---|
| `unlock` | `edge` | открыть ребро (как `_unlock` сейчас) |
| `noise` | `value` | добавить шум |
| `delay` | `value` | задержать агента окна (как `_apply_delay`) |
| `noop` | — | ничего |
| `engine_proposal` | ... | **применить его `fallback`** (см. ниже) |

Цену варианта бери из `cost.noise` и `cost.delay` **плюс** его `effects` — то, что раньше делали поля
`noise`/`delay` в `window.gd`. Порядок применения фиксирован: сначала цена, потом эффекты.

**Молчание — важное.** Качество (`good`/`neutral`/`bad`/`safe`) по-прежнему выбирает `_resolve_silence`
(кубик только там, D7) — это **не** переносится в данные. Из данных берётся набор эффектов для выбранного
качества: `silence[quality]`. Учти: у окна с триггером `locked_edge` в данных `unlock` стоит **во всех
четырёх** исходах — так описано фактическое поведение (`_unlock` в `_apply_silence` вызывается безусловно,
`sim.gd:449`), и это записано решением D37 в `docs/desions.md`. После перевода правило «молчание открывает
дверь» будет следовать из данных, а не из безусловного вызова, — убедись, что поведение не изменилось.

`engine_proposal` в данных — заявка на новую механику; ядро её не исполняет, а применяет `fallback`
(это условие приёмки артефактов контента, см. `02-format.md` §7). Эффект `fallback` применяй тем же
применятелем. Если `fallback` — массив, применяй по порядку.

### 4. Что НЕ делать

- Не менять `Mission.validate()`, `content/`-модули и форму данных.
- Не переносить в данные пороги эфира, прибытие группы, состояния людей, кубик импровизации: это законы мира
  (`architecture.md` §7, D7).
- Не менять состав событий и их поля.
- Не коммитить: изменения оставь в рабочем дереве, коммит делает ведущий после ревью.

## Обязательные ограничения проекта

1. Никаких `class_name` — только `const X := preload("res://...")`.
2. Имя константы `preload` не совпадает с классом движка (`Window` запрещено — уже `WindowScript`).
3. `sim/` не знает о нодах: только `RefCounted`.
4. Отступы — табы; идентификаторы английские, комментарии и русские имена тестов.
5. Детерминизм: обход в фиксированном порядке, никаких решений по порядку словаря.
6. Типизация: из `preload`-константы — `:=`; из функций без аннотации возврата — `=`; невыводимое — `: Variant`.

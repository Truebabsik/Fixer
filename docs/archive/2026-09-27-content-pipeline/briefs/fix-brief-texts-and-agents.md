## A. `Validator.validate(data)` без `texts` молча пропускает сверку ключей

`validator.gd:_check_texts` содержит `if not texts.is_empty() and not texts.has(...)`. Следствие: вызывающий,
забывший передать тексты, получает «проблем нет» — даже если в данных 19 ключей, которых никто не проверял.
Ты доказал это пробой, и именно поэтому положительный ассерт кейса скелета был вырожденным.

**Что сделать — сделать выбор явным, а забывание невозможным:**

1. `Validator.validate(data, texts)` — **параметр `texts` обязателен, значения по умолчанию нет.**
   Тогда `validate(data)` перестаёт компилироваться (GDScript: отсутствующий аргумент — ошибка), и «забыл»
   становится невозможно. Это дешёвый и жёсткий способ: типы вместо дисциплины.
2. Семантика значений:
   - `texts` — словарь → сверка ключей **выполняется** (в том числе для пустого словаря: «текстов нет»
     это осмысленное утверждение, и тогда все ключи данных — отсутствующие);
   - `texts == null` → сверка **не выполняется**, и это **явный отказ** вызывающего, написанный в коде.
3. Обнови **все** места вызова `Validator.validate` в репозитории: где тексты не проверяются — передавай
   `null` (это и есть «я не проверяю тексты», видно при чтении); где проверяются — словарь. То же для
   `Loader.load_mission(data, texts)`: если у него есть значение по умолчанию — убери, чтобы вызывающий
   выбирал явно. Проверь, что `load_mission` прокидывает выбор дальше без искажения.
4. **Проверки:** (а) `validate(data, null)` на данных с ключами — нет проблем про тексты (пропуск явный);
   (б) `validate(data, {})` на тех же данных — `MISSING_TEXT` на каждом ключе; (в) `validate(data, полный)`
   — чисто; (г) в кейсе скелета положительный ассерт должен стать **невырожденным**: он обязан краснеть,
   если сверку текстов случайно отключить (мутационная проба: подмени `_check_texts` на пустышку → кейс
   скелета краснеет, потому что его фикстура текстов больше не сверяется).

**Чего НЕ делать:** не заводить новый код проблемы вида «тексты не переданы». Явный `null` в коде читается
лучше и не требует правил: сам факт, что аргумент обязателен, и есть защита.

## B. `load_plan` не умеет выразить «бойцов нет»: `{"agents": []}` даёт состав по умолчанию

Ты это назвал сам: `{"agents": []}`, `{"agents": "мусор"}` и `[{"role":"comms"}]` дают `kira`+`echo`.
Для мусора «игнорировать поле» — принятое решение (C1). Но **`[]` — не мусор, а осмысленный пустой список**:
план говорит «бойцов нет», а получает двоих. Это не «игнорирование неверного поля», а подмена верного значения.

**Что сделать:**
1. **`{"agents": []}` → пустой состав.** Явно заданный пустой список уважается.
2. `{"agents": "мусор"}` → поле игнорируется, состав по умолчанию (как решено в C1). Разница между этими
   двумя случаями обязана быть видна в коде и покрыта проверками по отдельности.
3. `[{"role":"comms"}]` (элемент без `id`) — реши и обоснуй: либо такая запись отбраковывается целиком
   (у бойца нет идентификатора — это не боец), либо игнорируется только она. Молчаливая подстановка `""`
   в `id` недопустима: `Sim` пишет агентов в один словарь `positions`, и пустой id столкнётся.
4. **Про `sim/sim.gd:95,98` (`String(a["id"])`, `int(a.get(...))`) — не трогать** (чужая область, проверенный
   код). Но **назови в отчёте** явно: после твоих правок записи, приходящие из `Loader.load_plan`, всегда
   валидны, поэтому этот путь достижим только для плана, собранного руками. Это граница, и её надо записать,
   а не замолчать.

**Проверки:** четыре случая — пустой список, мусор вместо списка, элемент без `id`, корректный состав.
Каждый — с проверкой **точного** результата (размер и содержимое), а не «не пусто».

## 2. Как устроено решение (N2)

```gdscript
func _at(container, key, fallback = null):
	if typeof(container) == TYPE_DICTIONARY:
		return (container as Dictionary).get(key, fallback)
	if typeof(container) == TYPE_ARRAY and typeof(key) == TYPE_INT:
		var items := container as Array
		if key >= 0 and key < items.size():
			return items[key]
	return fallback


func _has(container, key) -> bool:
	return typeof(container) == TYPE_DICTIONARY and (container as Dictionary).has(key)
```

* `_at` — единственная точка охраняемого чтения; `_has` отдельно, потому что значение поля само
  может быть `null` и «поля нет» не должно выглядеть как «поле равно null».
* В `run()` охрана **не** пропускает проверки: при отсутствии места подставляется `{}` (или `[]`),
  поэтому `typeof(_at(...)) == TYPE_INT` становится НАЗВАННЫМ провалом, а циклы `for i in
  model_edges.size()` и обход помещений продолжают работать. Файл доходит до конца, а не обрывается
  на первой же отсутствующей записи.
* В `_*_of` отсутствующее поле даёт метку `NO_FIELD` в паре — пропажа поля ВИДНА в сравнении,
  а не роняет функцию рантаймом.
* Почему пришлось тронуть `_*_of`, хотя ревьюер написал «`_edges_of`/`_nodes_of`, которые уже
  безопасны»: безопасны они только по РАЗМЕРУ. По КЛЮЧУ они читали напрямую (`e["locked"]`,
  `p["period"]`, `node["floor"]`, `s["id"]`) — это доказано пробами B5–B8 (§3): каждая из этих
  мутаций писала `SCRIPT ERROR` и оставляла ассерт «…целиком» сравнивать `null` с `null`.

## 6. Решения шире буквы брифа

1. **Охрана `_*_of` (сверх четырёх названных сайтов).** Бриф называл `by_json.edges[3]`,
   `nodes["it4"]`, `patrols[0]`, `by_code.edge(...)["locked"]`, а ревьюер — что `_edges_of`/`_nodes_of`
   «уже безопасны». Пробы B5–B8 показали обратное: эти функции читали поля напрямую, и мутация
   «запись пришла без поля» давала `SCRIPT ERROR` и ВАКУУМНОЕ сравнение `null == null` в ассерте
   «…целиком» (B8 — при этом кейс ЗЕЛЁНЫЙ, код 0). Это тот же класс, что N2, и он в том же файле,
   поэтому четыре хелпера переведены на `_at`/`NO_FIELD`. Что это дало и чего НЕ дало — честно
   в §7.3.
2. **Охрана посылки §6 (`json_parsed`).** Ревьюер её не называл, но это те же прямые чтения
   `["edges"][3]`, `["nodes"]["it4"]`, `["patrols"][0]`. Проба B9/A9 показывает, что она достижима
   без всякого боевого кода: достаточно правки самого канона кейса (`"patrols": []`) — до правки
   аборт на `:458` с нулём ассертов, после — два названных провала.
3. **Ссылка на строки в тексте комментариев** дана по редакции ДО правки (`:460`, `:462`, `:463`,
   `:458`, `:581`, `_edges_of:170`, `_patrols_of:180`, `_nodes_of:161`, `_sensors_of:188`) — так
   они читаются в транскриптах проб; после правки номера сдвинулись, и это ожидаемо для цитаты пробы.

То есть: боевой код `sim/` падает рантаймом внутри себя, печатает десятки `SCRIPT ERROR`, а кейс
возвращает **код 0 и 174 ассерта**. Это класс чек-листа §3 («ворота, возвращающие успех с ошибкой
в логе») — и он в `game/sim/**`, который брифом запрещён к правке. Именно поэтому охрана `_nodes`
в `_sensors_of` со стороны кейса недостижима: любая запись сенсора без `nodes` роняет
`validate()`/`is_visible` раньше, чем кейс прочитает поле. Не правил, выношу ведущему (§8).

### 7.3. Проба A8: охрана не меняет вердикт

A8 — единственная из девяти «после»-проб, где вердикт не изменился (код 0 до и после). Что реально
изменилось: до правки кейс печатал шесть `SCRIPT ERROR` и ассерт «сенсоры целиком» сравнивал
`null == null`; после — прогон чистый, ассерт снова сравнивает значения (при несимметричной поломке
он покраснеет по имени). Дефект «сенсор без `id`» не диагностируется этим кейсом и не может: все три
пути строят сенсоры одним `add_sensor`, поэтому сравнению нечего противопоставить — это та же
граница независимости эталона, что и в §9.1 отчёта (M5/N3), а ловит дефект набор (`test_content_loader.gd`,
`test_windows_data.gd` — проба B8-full: `tests: 685, failed: 2`, код 1). Названо прямо, чтобы
«охрана добавлена» не читалось как «дефект теперь ловится этим кейсом».

### 7.4. Прочее

* Числа `168`, `621 из 900`, `900` в комментариях кейса (`:165`, `:480`, `:493`) — цитаты проб
  на редакции ДО правки, и это в тексте названо («проба до правки», «обе пробы»). Числа «152/0 и 884/0»
  из прежней редакции комментария §6 убраны как устаревшие и непроверенные здесь.
* `test_three_paths.gd` не отслеживается git — дельты по нему нет, редакции различаются только по SHA
  (до `93F7BA7A…`, после `3B59C7C0…`); в отчёте это указано дважды, чтобы числа проб нельзя было
  отнести не к той редакции.
* Дефектов в `game/sim/**`, `game/content/**`, `game/tests/fixtures/**` не искал целенаправленно
  (вне области); найденное в `sim/` — §7.2, оно найдено попутно, пробой.

## 8. Открытые вопросы (решения за ведущим)

1. **Чистить ли неохраняемую индексацию по всему `game/tests/**`?** `test_windows.gd:44`,
   `test_harness.gd:83`, `test_content_loader.gd:87/136` дают `LOAD FAIL` вместо диагноза на тех же
   мутациях (§7.1). Класс тот же, что N2, но файлы вне области этой правки.
2. **`game/sim/**`: прогон зелёный при потоке `SCRIPT ERROR`** (`sim.gd:243`, `mission.gd:115` — §7.2).
   Нужна ли отдельная задача? Правка в `sim/` брифом запрещена.
3. **Оставить ли охрану `_*_of`?** Она не меняет вердикт ни на одной из проб (§7.3), её эффект —
   устранение рантайм-ошибки из лога и возврат ассерту «…целиком» способности сравнивать значения.
   Если ведущий считает это расширением области — откат локален (четыре функции + `NO_FIELD`), на
   охрану четырёх названных сайтов он не влияет.

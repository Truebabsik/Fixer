## 5. По задачам

### Задача 3 — ADDRESSED

Проверено своим прогоном и пробами:

1. **Перечень — ровно перечень брифа.** Сравнил три списка машинно: `REQUIRED_TEXT_KEYS` в
   `validator.gd:85–98`, независимый эталон `REQUIRED_TEXTS` в `test_content_validator.gd:20–33` и список
   из брифа — 32 ключа, совпадение поэлементное и в обоих файлах (`validator == brief: True`, `test == brief: True`).
   В поставке `texts.ru.json` присутствуют все 32 (`required keys missing: none`, всего 167 ключей).
2. **Диагноз называет ключ и причину.** Проба T3-N даёт дословно
   `MISSING_REQUIRED_TEXT texts.log.silence :: «обязательного ключа «log.silence» нет в текстах: он относится к
   системе, а не к окну, и из данных миссии не выводится»`. Путь — в пространстве имён текстов, а не выдуманное
   поле данных: обоснование нового кода (вместо `MISSING_TEXT`) в отчёте 03 §2 состоятельно.
3. **Один ключ — один диагноз.** Проба T3-P: удаление `mission.01.title` даёт ровно `MISSING_TEXT title_key`;
   снятие охраны (T3-Q) краснит три именованных ассерта. Ложных срабатываний на поставке нет (положительные
   ассерты зелёные), лишнего требования нет — проба G отчёта 03 (добавление ключа в список) краснит 55
   положительных проверок, и это тот же механизм, что я вижу в обратную сторону.
4. **Проверка не идёт при `texts = null`.** Ассерт 12а (`test_content_validator.gd:1070`) существует и
   **дискриминирует**: проба T3-S (подмена `null` на `{}`) краснит именно его имя.
5. **Кейс есть и на положительное, и на два отрицательных, и по каждому ключу** (14, 14а–14г), эталон в тесте
   не зависит от проверяемого. Комментарий-долг над `UNUSED_OK_PREFIXES` переписан и описывает фактическое
   состояние (`validator.gd:100–117`).

### Задача 5 — ADDRESSED

1. **Инструмент — не кейс и не ворота.** `measure_mission01.gd` отсутствует и в `suite.gd:13–34` (`CASES`),
   и в `preflight.gd:27–44` (`MODULES`); `preflight` печатает `scripts: 33` = 13 модулей + 20 кейсов, то есть
   замер в разбор не входит. Свой вердикт — свой код возврата (0 на трёх моих прогонах).
2. **Числа инструмента совпадают с `scales.md` §10.1.** Сверил построчно: 76.9 % → 65.5 %, окон 174 → 207,
   `no_orders` 5 → 19 при `jammed` 20, `w_echo_reads` 0 → 16, таблица исходов до/после (см. §3.3),

## 7. Находки

**Critical — 0. Important — 0.** Ниже пять Minor; ни одна не меняет вердикт и не требует остановки волны.

### 7.1 Minor. Правило 0 `_withdraw_route` не покрыто ни одним ассертом и подменяется правилом 2

Что сделано: проба T8-A — из `sim.gd:344` убрано условие `here == exit_node` (осталось `exit_node == ""`).
Прогон: `tests: 1134, failed: 0`, код 0 — **набор остался полностью зелёным**, то есть ни один ассерт не
держит это правило.

Дополнительно проверил, что это не «недостижимая ветка»: собрал в копии сценарий ровно той формы, которая
названа в комментарии правила («отставший стоит в выходе в момент взятия цели» — в миссии 01 это отставший в
`hall0`, узле перед целью `archive0`), и прогнал его с правилом и без:

```
# с правилом 0
step 4: kira=goal echo=b obj=true
RESULT kira=b echo=b obj=true outcome=extracted escaped=["kira", "echo"] waypoints_echo=["b"]

# без правила 0
step 4: kira=goal echo=b obj=true
RESULT kira=b echo=b obj=true outcome=extracted escaped=["kira", "echo"] waypoints_echo=["b"]
```

Поведение **идентично**: в этом состоянии `_exit_ahead` (правило 2) уже возвращает `[here]`, потому что
`plan.route[waypoint_index - 1] == here` — а агент, стоящий в выходе и шедший по маршруту плана, этому
инварианту всегда удовлетворяет. Правило 0 срабатывает иначе только при нарушенном инварианте («индекс
маршрута не совпадает с узлом») — то есть это защита в глубину того же класса, что названная в отчёте 08 §5
ветка в `_exit_ahead` (её исполнитель честно назвал непроверенной).

Почему это находка, а не придирка: комментарий (и §2.3 отчёта) обосновывает правило 0 как несущее —
«Отправь мы уже пришедшего дальше — группа не собралась бы никогда», — а проба показывает, что от этого
защищает правило 2, а не правило 0. Это форма §6 чек-листа (ложное обоснование) плюс форма §2 (ветка без
проверки). Правка дешёвая: либо назвать правило 0 защитой в глубину (как это сделано для ветки `_exit_ahead`),
либо добавить ассерт на нарушенный инвариант.

# Ревью 1: контракт и ядро — `trace_key`, «ребро запираемо», снятие тревожной блокировки

Ревьюер: отдельный агент (не исполнитель). Бриф: `docs/current/2026-09-27-mission-01-accept/review-brief.md`.
Бриф исполнителя: `briefs/01-contract-core.md`. Отчёт исполнителя: `reports/01-contract-core.md`.
Общая часть: `docs/agents/constraints.md`, `docs/agents/review-checklist.md`.

**Вердикт: ADDRESSED по всем пунктам брифа; находок Critical 0, Important 2, Minor 4 — «с правками».**
Код делает ровно то, что требовал бриф, гейт зелёный, все требуемые мутационные пробы краснеют
именованными ассертами. Правки не вносил (роль ревьюера), редактор не запускал, коммит не делал.

## Методика

* Гейт — три команды `constraints.md` §2 на **текущем** рабочем дереве (`game/`), до правок и без них.
* Пробы — на копиях дерева в `%TEMP%` (робокопия всего дерева без `.git`, `.godot`, `tools`,
  `.superpowers`; `docs/` в копии есть). Движок запускался из боевого дерева,
  `--path <копия>\game`. Копии: **A** = текущее дерево, **B** = A с четырьмя боевыми файлами из `HEAD`,
  **C** = полностью `HEAD` (и боевые файлы, и тесты, и `suite.gd`; новый кейс удалён).
* Откат каждой пробы — копированием файла из эталонного снимка + сверка SHA256.
  Анкеры мутаций строились из `[char]9`/`[char]10` (LF-переводы, табы) и проверялись обратным
  поиском в файле до прогона — первые заходы на «таб против пробела» дали ложнозелёный прогон,
  который был отброшен и переделан (см. §5, проба 9).
* Копии и временные скрипты удалены, боевое дерево не менялось (SHA до/после — §9).

### Проба 9. Память окна: по одной записи и обе сразу

`sim.gd:501-505`; мутации — `if wid != "":` → `if false:` и `if edge_id != "":` → `if false:`.

```

FAIL  test_windows_data.gd :: повторный вход в сенсор окна не открывает

--- обе памяти отключены ---

```

**Оговорка исполнителя верна**: ассерт «окно у перекрытого ребра не открывается второй раз»
держится объединением двух памятей (снятие любой одной оставляет его зелёным). Уточнение:
снятие только `fired_windows` всё же краснит другой ассерт (`test_windows_data`), а снятие только
`fired_edges` **не краснит ничего во всём наборе** — это отдельная находка (Minor 2, §8).
Первые заходы этой пробы были ложнозелёными из-за анкера с пробелами вместо табов; проба
переделана с проверкой применённой мутации по содержимому файла.

## 6. Расхождение условий (пункт 3 брифа): расхождения нет

`_is_blocked_for(a, e)` (`sim.gd:369-372`) — единственное место, где решается «этот агент сейчас
не пройдёт по этому ребру». Вызовов ровно два: запрет шага `sim.gd:212` и выбор актора
`sim.gd:442`; своих копий условия в файле не осталось (`_is_locked` вне `_is_blocked_for`
используется только как гейт события, `sim.gd:216`).

Остаточные различия между двумя вызовами — **не в проходимости ребра, а в допуске агента**,
и оба старше задачи (в `HEAD` они те же, проверено чтением копии B):

* `_advance_own` пропускает агента с `delay > 0`, `_actor_before_locked_edge` — нет;
* `_actor_before_locked_edge` пропускает агента в `plan.exit_node`, `_advance_own` — нет.

Первый случай достижим только если у ребра два разных окна (`delay` накладывает окно на своего
агента, а окно на то же ребро по §4.2 не заводится вторым), второй — прежнее правило выбора
актора. Ни один из них не порождает класса «окно молча не срабатывает»: причиной тому было
именно `_is_locked` в выборе актора, и оно убрано.

### Important 1. Правило «запираемо тревогой» статично, а окно срабатывает только у СТОЯЩЕГО агента — сцена ★27 может не сыграть, и валидатор этого не увидит

### Important 2. Обоснование проверки типа `trace_key` ложно, а её ассерт слеп ко второму диагнозу

* `validator.gd:1000-1006`: комментарий утверждает, что без проверки типа автор получил бы
  «чужой диагноз — `DANGLING_TEXT` про текст, которого он не терял, **вместо** `WRONG_TYPE`
  про поле». Проба (ниже) показывает: проверка типа **добавляет** `WRONG_TYPE`, а чужой
  `DANGLING_TEXT` остаётся. То есть заявленная цель правки не достигнута.
* Проба (копия A, фикстура `_good()` c `trace_key`, тексты из `_texts_for()`):

```

    DANGLING_TEXT  texts.ap.ap_hall.trace

    WRONG_TYPE     access_points[0].trace_key
```

* Это ровно класс 7 чек-листа («одна ошибка — одно следствие», шапка `validator.gd`), и ровно

  каскад структурно невидим — проверка проверяет половину картины.
* Диагноз появился не в этой задаче (до неё на `trace_key: 5` выходили `UNKNOWN_KEY` +

  (`trace_key` — честные строки) не затронуты. Но комментарий и ассерт надо привести
  в соответствие с поведением (либо гасить `DANGLING_TEXT` по уже названному `WRONG_TYPE`,
  либо честно записать в комментарии, что диагнозов два).

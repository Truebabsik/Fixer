# Task 7 — Сенсоры и призраки: отчёт

## Что реализовано

Правило видимости и старения призраков в детерминированном ядре (`game/sim/sim.gd`):

- `var ghost_reported: Dictionary = {}` — рядом с `visible_last` (строка 25). Сброс в `setup()`
  (`ghost_reported = {}`) и заполнение в цикле по охране (`ghost_reported[g.id] = false`) рядом
  со снимком разведки `ghost_positions` / `visible_last`.
- `is_visible(guard) -> bool` — охрана видна, если её текущий узел покрыт хотя бы одним сенсором
  миссии (`mission.sensors[].nodes`).
- `ghost_mismatch() -> bool` — истина, если у любого патруля призрак (`ghost_positions`) не
  совпадает с реальным узлом. Обход идёт по массиву `guards` в порядке добавления, без опоры на
  порядок `Dictionary`.
- `_update_visibility()` заменяет заглушку `pass` из Task 6 и вызывается в прежнем месте цепочки
  `advance()` (часы → эфир → своё движение → движение охраны → видимость → цель → конец):
  - `sensor_contact` — только на **восходящем фронте** видимости (был невидим → стал виден);
  - `ghost_mismatch` — **однократно на патруль** за операцию: щёлкает `ghost_reported[g.id] = true`
    перед `_emit`, поэтому поток событий не образуется.

Все три метода взяты из брифа **дословно**, имена и сигнатуры не менялись. Комментарий-заглушка
«Заготовки под Task 7; пока ничего не делают» удалён вместе с `pass` — он перестал быть правдой.

Почему так, по смыслу задачи: игрок всегда видит весь план и только через сенсоры — реальную
охрану; вне сенсоров он видит призраков, замерших там, где их застала разведка. Расхождение
призрака с реальностью и есть индикатор тревоги (D16), поэтому оно сообщается один раз на переход
состояния — повторяющееся событие приучило бы игрока его игнорировать.

## Self-review

- **Дословность.** Тело теста и три метода сверены с брифом построчно; имена тестов не переписаны,
  сигнатуры (`is_visible(guard) -> bool`, `ghost_mismatch() -> bool`) сохранены. Отступы — табы.
- **Правило типизации.** `var seen := is_visible(g)` корректен: у `is_visible` есть аннотация возврата.
  Аннотированных возвратов у хелперов не добавлено; в тесте `var m = Fixture.build()` оставлен с `=`,
  как требует правило (у `build()` аннотации нет). Явных аннотаций, ломающих динамику, не вводил.
- **Чистота `sim/`.** Ни `Node`, ни `SceneTree`, ни сцен, ни рендера: только `RefCounted` и данные
  миссии. `class_name` не добавлен нигде.
- **Детерминизм.** Оба цикла обходят массивы (`guards`, `mission.sensors`) в порядке добавления;
  итерации по `Dictionary` нет. `ghost_mismatch()` возвращает первый же найденный случай в порядке
  `guards`. Повторный прогон идентичен.
- **Однократность события.** Ключ счётчика — `g.id`; флаг ставится **до** `_emit`, поэтому даже при
  нескольких патрулях в одном узле дубля на патруль не будет. `sensor_contact` дублируется только при
  реальном новом переходе «невидим → видим» (включая повторный вход в зону), что соответствует
  формулировке «по одному на переход состояния, не каждый шаг».
- **Обратная совместимость.** Существующие 63 ассерта не тронуты и остались зелёными; заглушка
  `_check_objective`/`_check_end` не затронута (Tasks 8–11).
- **Вердикт.** Код возврата — единственный сигнал; шум `stderr` про `user://logs` и корневые
  сертификаты присутствует и в красном, и в зелёном прогоне, то есть к задаче отношения не имеет.

## Замечания и риски

1. `ghost_reported` не сбрасывается при повторном совпадении призрака с реальностью: расхождение
   сообщается один раз за операцию на патруль. Это соответствует брифу и смыслу D16 (однократный
   сигнал вместо потока), но если в поздних задачах понадобится «повторная тревога» при новом
   расхождении после восстановления контакта, флаг придётся сбрасывать при возврате к совпадению —
   отдельное решение, за рамками Task 7.
2. `ghost_positions` сознательно не обновляется при появлении охраны под сенсором: бриф называет
   призраков снимком разведки, а не «последним известным положением». Если П2 захочет обновлять
   снимок при контакте, это изменит семантику `ghost_mismatch` и должно быть отдельной задачей.
3. `is_visible(guard)` ожидает объект с полем `node` (Agent). Это ровно интерфейс из брифа; при
   передаче `Dictionary` будет рантайм-ошибка. Для вызывающих из UI стоит помнить, что передавать
   надо элемент `sim.guards`.
4. Ключи `ghost_positions` / `visible_last` / `ghost_reported` различают патрули по `id`. Две записи
   патрулей с одинаковым `id` в миссии перекрыли бы друг друга; уникальность `id` нигде в ядре не
   проверяется (кандидат на валидацию миссии в другой задаче).

## 1. Что реализовано

Создан `game/sim/radio.gd` — чистая модель радиоэфира (`extends RefCounted`, без
`Node`/`SceneTree`/сцен/рендера). Эфир — **отдельная шкала** от шума команды (D33):
наказание за разговор попадает в право голоса, а не в безопасность группы.

Числа взяты из `docs/spr/scales.md` §3.1 дословно, без подгонки:

| Константа | Значение | Смысл |
|---|---|---|
| `PER_TRANSMIT` | `8` | приказ в эфир |
| `IMPRINT_PER_TRANSMIT` | `1` | отпечаток за передачу |
| `DECAY` | `2` | затухание эфира |
| `DECAY_PERIOD` | `5` | за каждые 5 шагов |
| `JAM_THRESHOLD` | `12` | порог глушения |
| `JAM_STEPS` | `8` | шагов без права голоса |
| `IMPRINT_INTERCEPT` | `3` | порог перехвата |

Состояние: `radio: int`, `imprint: int`, `jam_until_step: int = -1`.
Интерфейс: `transmit(step) -> Dictionary` (`radio`, `imprint`, `jammed`,
`intercepted`), `tick_decay(step) -> void`, `can_speak(step) -> bool`,
`is_intercepted() -> bool`. Ровно как в блоке Interfaces брифa.

Свойства, зафиксированные кодом:
- **Эфир затухает, отпечаток — нет.** `tick_decay` трогает только `radio`;
  `imprint` не смывается никогда — след передатчика вечен.
- **Затухание дискретное:** `step % 5 == 4`, то есть −2 ровно на 5-м, 10-м,
  15-м шаге (не «каждые пять вызовов»).
- **Затухание не уходит в минус:** `maxi(0, radio - DECAY)`.
- **Глушение ставится только из «говорящего» состояния** (`radio >= 12 and
  can_speak(step)`): передача в уже заглушённом канале не продлевает немоту,
  `jam_until_step` не сдвигается. Это прямо следует из кода брифa и разобрано
  в разделе 5.

## 4. Самопроверка

Прогнал по фактическому коду, а не по памяти:

1. **Пункт 1 кейса (две передачи подряд).** `transmit(0)`: `radio = 8`,
   `can_speak(0)` → `0 >= -1` истина. Второй `transmit(0)`: `radio = 16 >= 12` и
   `can_speak(0)` истина → `jam_until_step = 8`, `jammed = true`,
   `can_speak(0)` → `0 >= 8` ложь. Совпадает с четырьмя ассертами пункта.
2. **Пункт 2 (немота 8 шагов).** Тики на шагах 0..7: затухание срабатывает на
   `step % 5 == 4`, то есть на шагах 4 и 7 → `radio 16 → 14 → 12`. Шаг после цикла
   равен 8, `can_speak(8)` → `8 >= 8` истина. Право голоса возвращается ровно на
   8-м шаге — граница включительная.
3. **Пункт 3 (паузы).** `r2` передаёт на шагах 0, 10, 20, между ними по 10 тиков.
   Первый тик после передачи идёт с тем же `step` (0 % 5 ≠ 4, затухания нет), тик
   на шаге 5 вычитает 2. К моменту шага 10 эфир 8 − 2 = 6, дальше не меняется

   срабатывает**. Пункт 3 при этом проверяет только `can_speak(29)` и
   `is_intercepted()`; на шаге 29 `jam_until_step = 18`, значит `can_speak` истина,

   «с паузами не заглушили» читается как «эфир ниже порога» — фактически эфир
   пересекает порог и канал глушится; тест этого не требует и не проверяет, но
   поведение стоит знать (см. раздел 5).
4. **Пункт 4 (затухание).** Пять тиков с шагами 0..4 → срабатывание только на
   шаге 4, `radio 8 → 6`. Ещё пять тиков с шагами 5..9 → срабатывание на шаге 9,
   `radio 6 → 4`. Отпечаток не тронут.
5. **Пункт 5.** `imprint` остаётся `1`: `tick_decay` его не касается.
6. **Отсутствие запрещённых сущностей.** `Select-String` по `radio.gd` на

## 5. Замечания и риски

1. **Три передачи с паузой 10 всё же глушат канал.** Как показано в п. 3
   самопроверки: эфир 6 + 8 = 14 ≥ 12, на шаге 10 канал рвётся до 18-го шага.
   Кейс этого не ловит, потому что проверяет `can_speak` только на шаге 29, уже
   после восстановления. Это **не повод менять числа** — правка констант запрещена
   условиями задачи, а тест из брифa проходит. Но формулировка брифа «три передачи
   с паузами: канал чист» справедлива только для момента проверки, а не для всего
   интервала. Для задачи 8 (выдача приказа) это значит, что приказ, поданный в
   паре шагов после третьей передачи, будет **съеден глушением** — ровно тот
   сценарий, который §3.1 справочника называет штатным («часть приказов может быть
   съедена глушением»). Считаю это осознанным поведением модели, а не дефектом,
   и фиксирую как известную характеристику для потребителей `can_speak`/`transmit`.
2. **Передача в заглушённом канале копит эфир и отпечаток, но не продлевает
   немоту.** `can_speak` стоит в условии постановки глушения, поэтому игрок в
   немоте может «кричать в пустоту»: `radio` и `imprint` растут, `jam_until_step`
   не сдвигается. Значит, перехват можно накликать передачами во время глушения.
   Код принят дословно из брифa, поведение не менял. Стоит подтвердить у дизайна,
   намеренно ли это (для задачи 8 это развилка: разрешать ли приказ в немоте).
3. **`jam_until_step = -1` как «никогда не глушили»** делает `can_speak` истинным
   на любом шаге ≥ 0. Пока шаги неотрицательны, это корректно; отрицательный шаг
   в `can_speak(-5)` вернул бы ложь. Контракт «шаг — неотрицательный» задаётся
   вызывающим (задача 6), сам модуль его не проверяет.
4. **Зависимостей нет** — модуль не потребляет `scales.gd` и не тянет `Assert`.
   Готов к потреблению из задачи 6 (`tick_decay(step)` в цикле шага) и задачи 8
   (`can_speak(step)` / `transmit(step)` при выдаче приказа).
5. **Документация не трогалась.** `docs/spr/scales.md` §3.1 уже описывает числа
   верно; новых дизайн-решений, требующих `docs/desions.md` или
   `docs/architecture.md`, задача не вносила. В объём входили ровно три файла.

# Раунд исправлений 1 — решение контролёра по замечанию 1 (D34)

**Статус:** DONE
**Коммит раунда:** `d20fbd7` fix(sim): затухание эфира -4 за 5 шагов и тест на глушение за весь ход (D34)
**Основание:** решение контролёра, уже зафиксированное в `e00bc02` (D34 в
`docs/desions.md`, правка чисел в `docs/spr/scales.md` §3.1).

## 1. Суть решения

Контролёр признал замечание 1 (раздел 5 выше) правильным: **числа были неверны,
структура кода — нет.** Арифметика: при `+8` за передачу и затухании `−2` за 5
шагов три передачи с паузой 10 дают `8 → 4 → 12 → 8 → 16`, и две передачи подряд
дают ровно то же `16`. То есть два разных режима поведения численно неразличимы —
ни один порог глушения не смог бы их разделить. Разделяющий параметр — **скорость
затухания, а не порог**.

Постановлено: **затухание `−4` за 5 шагов.** Порог глушения `12`, передача `+8`,
отпечаток `+1`, перехват `3` — без изменений. При `−4` пауза в 10 шагов опустошает
эфир (`8 → 0`): три передачи с паузами проходят чисто, две подряд по-прежнему
набирают `16` и глушат. Градиент замысла: пауза ~10 шагов между приказами
безопасна, пауза ~5 шагов уже глушит (`4 + 8 = 12`).

Замечание 2 закрыто как **не-проблема**: `order()` отказывает, пока `can_speak`
ложно, поэтому `transmit()` в немоте не вызывается вовсе. Код не менялся.

Бриф пересмотрен: исправлен `DECAY := 4` и заменён ассерт пункта 3. Старая
проверка смотрела `can_speak` только в **конце** последовательности и потому
пропускала модель, в которой паузы не помогали вообще. Новая отслеживает
`jammed_ever` — глушило ли **хоть раз** за весь ход; ожидания затухания меняются с
`8 → 6 → 4` на `8 → 4 → 0`.

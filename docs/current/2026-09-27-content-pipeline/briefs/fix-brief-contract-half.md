### 1 (Important). Вторая половина контракта не охраняется ничем

Контракт гласит: при неверном типе `texts` выдаётся `WRONG_TYPE` и **сверка не выполняется**. Проверяется
только первая половина. Все три выбранных значения-нарушителя — `"мусор-строка"`, `7`, `false` — **не имеют
метода `has`**, поэтому `_check_texts` падает на первой же строке рантаймом, и каскад `MISSING_TEXT` не
наступает ни при верном коде, ни при сломанном.

**Проба ревьюера:** сломал так, что `WRONG_TYPE` добавляется, но `_check_texts` вызывается **всегда**
(грубая ошибка «сверку ведём не тем»):
```
### E: сверка не пропускается
tests: 727, failed: 0
EXIT=0
```
Ни один из 727 ассертов не покраснел, хотя наблюдаемое поведение изменилось: `validate(_good(), [])` даёт
`["WRONG_TYPE"]` в верном коде и `["WRONG_TYPE", "MISSING_TEXT"×5]` в сломанном — потому что **у `Array` метод
`has` есть**. То есть имена ассертов «ровно `WRONG_TYPE`, без сверки» держатся только на том, что выбранные
типы падают раньше. Вдобавок мутация возвращает на зелёном прогоне `SCRIPT ERROR … Nonexistent function 'has'
in base 'String'` в stderr — тот самый капкан §6.1.1 (stderr не вердикт).

**Что сделать (боевой код правки НЕ требует):** добавь в корпус неверных типов значение, у которого метод `has`
**есть** — `[]` (или `PackedStringArray(["a"])`). Тогда верный код даёт ровно `["WRONG_TYPE"]`, а сломанный
(сверка всё равно идёт) — шесть кодов. Правь **оба** существующих цикла: `test_content_validator.gd:855`
(кейс 12в) и `test_content_loader.gd:218` (кейс 7а).

**Проверка обязательна:** воспроизведи мутацию E (сверка вызывается всегда) и покажи, что теперь набор
**краснеет**, называя ассерт. Без этого правка не считается сделанной: именно так этот дефект и прятался.

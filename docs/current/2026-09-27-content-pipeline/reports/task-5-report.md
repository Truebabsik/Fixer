четыре исхода молчания читаются из `Mission.data["windows"]` (авторская форма,

Латентный дефект из находки задачи 4 закрыт: сработавшее окно запоминается, и окно
у всё ещё запертого ребра больше не открывается каждый шаг. Это проверено не только

**Полный гейт сейчас красный по чужой причине.** Последний прогон: `tests: 429,

## 2. Сужение области и решение ведущего

Ведущий сузил область на время параллельной правки `game/content/*` и
`game/tests/cases/test_content_*.gd`: эти файлы я не трогал вообще, новые проверки
живут в отдельном кейсе `game/tests/cases/test_windows_data.gd`, в `suite.gd`
добавлена одна строка.

При этом всплыл конфликт, который ведущий разрешил отдельным сообщением: в
`test_windows.gd` две локальные миссии (`_make_b_side()`, `_make_reverse_side()`)
собирались кодом **без** `set_data`, то есть без раздела `windows`. После перевода

разрешена точечная правка `test_windows.gd` (ровно два вызова `set_data`, ни одного
ассерта). Вариант B (legacy-фолбэк «нет раздела `windows` → открывать окно из
`WindowScript.locked_door`») отклонён по существу: такой фолбэк молча скрывает
забытое в контенте окно. Ядро осталось строго data-driven.

## 3. Что изменено по файлам

### 3.1 `game/sim/window.gd` — рантайм-форма из данных

Удалён `locked_door(edge_id, agent_id)` (единственный потребитель — старый
`_maybe_open_window`). Вместо него:

```gdscript
## Вид окна в рантайме по типу триггера. У запертого ребра вид исторический,
## `locked_door`: на это имя смотрят события, тесты и решение D37.
static func kind_for(trigger_type: String) -> String:
	if trigger_type == "locked_edge":
		return "locked_door"
	return trigger_type


## Поле триггера, за которое окно держится: ребро, помещение, сенсор. Оно же —
## вторая половина составного id окна и поле события `window_opened`.
static func anchor_key(trigger_type: String) -> String:
	match trigger_type:
		"locked_edge":
			return "edge"
		"node_entered":
			return "node"
		"guard_in_sensor":
			return "sensor"
	return ""


static func from_data(w: Dictionary, agent_id: String) -> Dictionary:
	var trigger = w.get("trigger", {})
	var type := ""
	var anchor_id := ""
	if typeof(trigger) == TYPE_DICTIONARY:
		var trigger_dict: Dictionary = trigger
		type = String(trigger_dict.get("type", ""))
		anchor_id = String(trigger_dict.get(anchor_key(type), ""))
	var kind := kind_for(type)
	var out := {
		"id": "%s:%s" % [kind, anchor_id],
		"kind": kind,
		"agent": agent_id,
		"text_key": String(w.get("text_key", "")),
		"options": _options(w),
		"silence": _silence(w),
	}
	var anchor := anchor_key(type)
	if anchor != "":
		out[anchor] = anchor_id
	return out
```

* `_options(w)`: вариант рантайма = `id`, `text_key`, `complexity`, `noise` и `delay`
  из `cost`, `effects` списком. Ветка молчания добавляется **последней**:
  `{"id": WindowScript.SILENCE, "text_key": <silence.text_key>}` — поэтому
  `has_silence` и `order("silence")` работают как прежде.
* `_silence(w)`: карта `{good: [...], neutral: [...], bad: [...], safe: [...]}`;
  отсутствующее качество — пустой список (ядро не падает на неполных данных;
  валидатор такие данные до ядра не пропустит).
* `_effects(raw)`: эффект бывает массивом и одиночным объектом (`02-format.md` §7),
  оба формата приводятся к массиву; словари **копируются** (`duplicate(true)`),
  чтобы рантайм не делил состояние с неизменяемыми данными миссии.

Составной id сохранён дословно: `locked_door:<ребро>` для запертой двери,
`node_entered:<помещение>` и `guard_in_sensor:<сенсор>` для новых триггеров.
Зашитая строка `"text": "Дверь заперта, хотя в плане открыта."` и ярлыки `label`
заменены ключами контента (`text_key`): тексты теперь данные, а не код.

### 3.2 `game/sim/sim.gd` — триггеры из данных, один применятель эффектов

Новое состояние (сбрасывается в `setup()`):

```gdscript
## Учёт сработавших окон: id окна из данных -> true и ребро окна запертой двери ->
## true. Сбрасывается в setup(). Нужен, чтобы окно не открывалось второй раз:
## «одно окно — один срабатывающий раз» (`02-format.md` §4.2).
var fired_windows: Dictionary = {}
var fired_edges: Dictionary = {}
```

`_maybe_open_window()` переписан целиком:

```gdscript
func _maybe_open_window() -> void:
	if finished:
		current_window = null
		return
	current_window = null
	var windows = mission.data.get("windows", [])
	if typeof(windows) != TYPE_ARRAY:
		return
	for w in windows:
		if typeof(w) != TYPE_DICTIONARY:
			continue
		if _window_fired(w):
			continue
		var actor := _window_actor(w)
		if actor.is_empty():
			continue
		var agent_id := String(actor["agent"])
		_mark_window_fired(w)
		current_window = WindowScript.from_data(w, agent_id)
		_emit("window_opened", _window_event_data(w, agent_id))
		return
```

Триггеры (`_window_actor` → три функции, каждая возвращает `{"agent": id}` или `{}`):

| триггер | условие | кто «agent» |
|---|---|---|
| `locked_edge` | первый по `own` агент, стоящий перед **этим** ребром, и ребро заперто (`_is_locked`); правила пропуска прежние: мёртвый, дошедший до выхода, кончивший маршрут | свой агент |
| `node_entered` | в событиях **этого шага** есть `agent_moved` в это помещение | вошедший свой |
| `guard_in_sensor` | в событиях **этого шага** есть `sensor_contact`, а помещение контакта видно этому сенсору (`_sensor_sees`) | охранник из события |

`_step_events()` — события с `step == scales.step`; триггеры входа смотрят именно на
шаг, а не на «находится там давно» (иначе окно открывалось бы каждый шаг, как прямо
запрещено брифом §1).

Применение эффектов — один применятель:

```gdscript
func _apply_option(w: Dictionary, option_id: String) -> void:
	...
	_apply_cost(w, chosen)
	for effect in chosen.get("effects", []):
		_apply_effect(w, effect)


## Цена варианта: `cost.noise` и `cost.delay` из данных (прежде — поля варианта).
func _apply_cost(w: Dictionary, chosen: Dictionary) -> void:
	var noise := int(chosen.get("noise", 0))
	if noise > 0:
		scales.add_noise(noise)
	_apply_delay(w, int(chosen.get("delay", 0)))


func _apply_silence(w: Dictionary, eff: Dictionary) -> void:
	var by_quality: Dictionary = w.get("silence", {})
	for effect in by_quality.get(String(eff["quality"]), []):
		_apply_effect(w, effect)


func _apply_effect(w: Dictionary, effect) -> void:
	if typeof(effect) != TYPE_DICTIONARY:
		return
	var effect_dict: Dictionary = effect
	match String(effect_dict.get("type", "")):
		"unlock":
			_unlock(w, String(effect_dict.get("edge", "")))
		"noise":
			var added := int(effect_dict.get("value", 0))
			if added > 0:
				scales.add_noise(added)
		"delay":
			_apply_delay(w, int(effect_dict.get("value", 0)))
		"engine_proposal":
			_apply_fallback(w, effect_dict.get("fallback", []))
```

`_apply_fallback` принимает и массив, и одиночный объект, и применяет **тем же**
применятелем (рекурсия), по порядку массива. `noop` и неизвестный тип не делают
ничего. `_unlock(w, edge_id)` открывает ребро из эффекта, а если эффект ребро не
назвал — ребро окна (так же, как прежний `_unlock(w)`).

`_resolve_silence` не тронут: качество по-прежнему выбирает кубик по seed (D7), из
данных берётся только набор эффектов выбранного качества. Для окна запертой двери
`unlock` стоит во всех четырёх исходах (D37), поэтому правило «молчание открывает
дверь» теперь **следует из данных**, а не из безусловного `_unlock(w)` вне `match`.

## 4. Как устроен учёт сработавших окон

* Ключ — **id окна из данных** (`w["id"]`), как и просил ведущий. Для окна с
  триггером `locked_edge` дополнительно запоминается **ребро** (`fired_edges`):
  «повторное окно на то же ребро не поддерживается» (`02-format.md` §4.2) выполняется
  буквально, даже если в данных окажутся два окна на одно ребро.
* Отметка ставится **в момент открытия**, а не в момент ответа. Это безопасно:
  пока окно открыто, `advance()` не двигает мир и `_maybe_open_window` не вызывается;
  отказ (`no_orders`, `jammed`, `unknown_option`) окно не закрывает (проверки 4–5
  прежнего кейса), поэтому «открыто, но не отвечено» не может привести к повторному
  открытию.
* `fired_windows` и `fired_edges` сбрасываются в `setup()` — прогон воспроизводим.
  Это проверено новой проверкой 2в (тот же `Sim`, перезапущенный `setup` на той же
  миссии, обязан снова показать окно).
* Что именно закрыт дефект: окно, которое дверь **не** открыло (в данных нет
  `unlock`), прежде открывалось заново каждый шаг — теперь один раз. Проверки 2 и 2б
  строятся ровно на таких данных (`noop`), иначе дефект не был бы виден.

## 5. Как применяются эффекты

1. `order(option_id)`: проверка варианта → списание приказа → эфир → `_apply_option`.
2. `_apply_option`: сначала **цена** (`cost.noise`, затем `cost.delay` — порядок
   фиксирован брифом), затем **эффекты** в порядке массива, каждый через
   `_apply_effect`.
3. `order("silence")`: `_resolve_silence` даёт качество (кубик, D7) → берётся
   `w["silence"][quality]` → тот же применятель по порядку данных.
4. `engine_proposal` не исполняется: применяется его `fallback` (объект или массив,
   по порядку, тем же применятелем). Заявка `want`/`needs` на мир не влияет.

События не изменились: `order_issued {window, option, radio}`,
`order_silenced {window, effect}`, `order_refused {window, reason}` — те же поля и те
же значения. У `window_opened` для запертой двери набор полей дословно прежний
(`kind`, `edge`, `agent`) и `kind` = `locked_door`.

## 6. Рантайм-форма и события: принятые решения

1. **Вид окна.** `locked_edge` → `locked_door` (историческое имя, на него смотрят
   события, тесты и D37); `node_entered`/`guard_in_sensor` → сам тип триггера.
   Формула брифа «`<kind-без-_edge>:%s`» прочитана так: для триггеров без `_edge`
   вид — это тип триггера, для `locked_edge` — исторический `locked_door`. Вид
   выводится из `trigger.type`, а не из поля `kind` данных: иначе `kind` и `trigger`
   могли бы разойтись (валидатор значение `kind` не ограничивает).
2. **Порядок обхода.** Окна перебираются в порядке массива, внутри окна свои — в
   порядке `own`. Основание: `02-format.md` §9 — «порядок элементов в массивах =
   порядок проверки», то есть приоритет окна задаёт автор данных. Для одного окна
   (фикстура) это дословно прежнее поведение.
3. **Событие для новых триггеров.** `window_opened` для `node_entered` несёт поле
   `node`, для `guard_in_sensor` — `sensor` (плюс `kind` и `agent`). Класть id
   помещения в поле `edge` значило бы врать в данных события. Для запертой двери
   событие не изменилось ни на поле.
4. **`label` → `text_key`.** Рантайм-вариант больше не несёт русский ярлык: текст
   берётся по `text_key` из контента. Потребителей `label` в репозитории нет
   (презентации в `game/` пока нет).

## 7. Что именно ловят новые проверки (`test_windows_data.gd`)

| проверка | что ловит |
|---|---|
| 1 (`node_entered`, 18 ассертов) | окно открывается на **вход** в помещение: `kind`/`id`/`node`/`agent`/`has_silence`, событие несёт вид и помещение, автопауза (шагов нет), цена `cost.noise` + эффект `noise` вместе (шум 4), задержка цены (2 шага), затем агент идёт дальше и окно не возвращается |
| 2 (`locked_edge`, 10) | окно у запертого ребра **не срабатывает второй раз**: `wait` без эффектов (`noop`), дверь остаётся запертой, три шага подряд окна нет; ловит прежний дефект «окно каждый шаг» |
| 2б (2 ассерта) | то же для **молчания**: без `unlock` в данных дверь заперта, окно после молчания не возвращается |
| 2в (4) | память сбрасывается в `setup()`: `fired_windows`/`fired_edges` пусты и окно открывается снова (детерминизм прогона) |
| 3 (`engine_proposal`, 4) | применяется **`fallback`-массив**: `unlock` открыл дверь, `delay` задержал агента. Если `fallback` игнорировать — обе проверки падают; если «исполнять» заявку самой — тоже |
| 3б (3) | `fallback` **одиночным объектом**: шум +6, и ничего сверх него (дверь не открыта) |
| 4 (`guard_in_sensor`, 9) | окно открывается, когда охрана **входит** в зону сенсора (`kind`/`id`/`sensor`/`agent`/событие/эффект из данных), а повторный вход в зону (охрана с периодом 1 возвращается на третий шаг) окна **не открывает** |

Проверки смотрят на поведение (состояние мира, события, задержки), а не на наличие
полей: каждая падает при сломанной реализации — например, если убрать `_apply_cost`,
убрать `_mark_window_fired`, не разбирать `fallback` или искать триггер по «стоит в
узле», а не по «вошёл в узел».

## 9. Сомнения, решения и то, что заметил, но не стал делать

1. **`test_windows.gd` пришлось тронуть.** Без данных окна блоки 8/8б краснеют: ядро
   больше не придумывает окно само. Разрешено ведущим (вариант A), добавлено ровно
   два `set_data`; ассерты не тронуты. Файл `game/tests/fixtures/small_mission.gd` я
   **не** правил (запрещено): его комментарий «Ядро эти данные пока не читает: перенос
   — подготовка, чтение придёт следующей задачей» теперь устарел — прошу ведущего
   поправить одной строкой.
2. **Порядок обхода.** Выбрал «окна снаружи, свои внутри» (приоритет задаёт автор
   данных, `02-format.md` §9), а не «свои снаружи». Для фикстуры и для одного окна
   разницы нет; при двух окнах, годных одновременно, откроется раньше записанное.
   Если ведущий хотел приоритет по порядку своих — это правка одного цикла.
3. **Поля `kind` в данных не использую** для рантайм-вида (вывожу из `trigger.type`).
   Причина: валидатор значение `kind` не ограничивает, и расхождение `kind` с
   `trigger` дало бы окно с видом, не совпадающим с триггером.
4. **`text`/`label` удалены** из рантайм-формы, вместо них `text_key` у окна, у
   вариантов и у ветки молчания. Потребителей ярлыков в репозитории нет, но если
   презентация П2 ждала `label` — это осознанная смена контракта, её надо знать.
5. **`WindowScript.locked_door` удалён** как мёртвый код. Если он был нужен как
   публичный хелпер (например, для будущих инструментов), вернуть его — три строки,
   но он противоречит смыслу задачи.
6. **`architecture.md` §6.1 (`window_opened`) не правил.** Таблица перечисляет поля
   `kind`, `edge`, `agent`. Для запертой двери это по-прежнему ровно так; для новых
   триггеров якорь лежит в `node`/`sensor`. Документ стоит дополнить одной строкой —
   но это дизайн-документ, решение ведущего.
7. **Дизайн конвейера §4.1 говорит, что авторскую форму конвертирует загрузчик.**
   Задача 5 (бриф §1–§3) требует обратного: конвертирует ядро. Сделал по брифу —
   конвертация в `sim/window.gd`, авторская форма в `Mission.data["windows"]`
   остаётся нетронутой. Расхождение с §4.1 стоит зафиксировать (или поправить §4.1).
8. **`sensor_contact` не несёт id сенсора**, а менять поля событий брифом запрещено.
   Поэтому `guard_in_sensor` сопоставляет помещение контакта с зонами сенсоров через
   `mission.sensors` (`_sensor_sees`). Если позже понадобится точный сенсор в
   событии, это отдельное решение (и оно изменит состав полей события).
9. **`delay` у окна `guard_in_sensor` задерживает своего агента окна**, а окно сенсора
   открывает охранник — то есть `delay` в таком окне никого не задержит
   (`_apply_delay` ищет агента окна среди своих). Поведение соответствует брифу
   («задержать агента окна, как `_apply_delay`»), но это грабли контента: в окне
   сенсора осмысленны `noise`, `unlock` или `noop`. В данные не лез.
10. **Проверку «одно окно срабатывает один раз» для `node_entered` не сделал:**
    повторный вход в то же помещение требует маршрута с возвратом, а память
    сработавших окон проверена на запертой двери (сильнее — там дефект и был) и на
    сенсоре (охрана реально возвращается в зону). Если нужна именно эта пара —
    добавлю.
11. **Заметил, но не делал:** контракт `complexity` в рантайме сохранён (лежит в
    варианте), но ядром по-прежнему не читается (D36); `int()` от `value` эффекта
    молча превращает `1.5` в `1` — до ядра такое не дойдёт, валидатор требует int.
12. **Следствие требования «один раз», о котором стоит знать авторам контента:**
    окно запертой двери, в данных которого нет `unlock` ни в одном варианте и ни в
    одном исходе молчания, теперь оставляет группу перед запертой дверью навсегда
    (прежде окно возвращалось каждый шаг и давало «второй шанс»). Это ровно то, что
    просил бриф, и валидатор такую миссию не запрещает (п. 21 постановки —
    ограничение «только у locked_edge», а не требование наличия `unlock`). Проверка
    задачи 2 на стороне контента здесь была бы уместна — это чужая область, не трогал.

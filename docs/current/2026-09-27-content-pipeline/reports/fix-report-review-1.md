## C1. Неверный тип раздела валил загрузчик в рантайм внутри цикла

**Что изменено.**

1. `validator.gd:86` — новый `_check_sections`: для `edges`, `patrols`, `sensors`, `windows`,
   `intel`, `access_points` различает «ключа нет» (`MISSING_FIELD`) и «ключ есть, но не массив»
   (`WRONG_TYPE`). Список разделов — константа `ARRAY_SECTIONS` (`validator.gd:38`).
2. `validator.gd:63` — `validate()` вызывает `_check_sections` первым шагом и больше не
   проверяет тип `edges` в `_check_root_keys` (дубль снят, `_check_root_keys:139`).
3. `loader.gd:65` — `_items(data, section)`: не массив → пустой массив. Все четыре точки
   итерации/упаковки разделов (`loader.gd:45,47,51-53`) идут через него. Загрузчик физически
   не может войти в цикл по словарю.

**Доказательство, что C1 закрыт (проба до правки, дословно):**

```
VALIDATE: []
WATCHDOG: _initialize прервался
EXIT=1
SCRIPT ERROR: Invalid access to property or key 'id' on a base object of type 'String'.
   at: load_mission (res://content/loader.gd:41)
```

Валидатор молчал (`[]`), загрузчик падал внутри цикла. Проба после правки, все пять разделов:

```
SECTION patrols: mission=<null> problems=[WRONG_TYPE patrols]
SECTION sensors: mission=<null> problems=[WRONG_TYPE sensors]
SECTION windows: mission=<null> problems=[WRONG_TYPE windows]
SECTION intel: mission=<null> problems=[WRONG_TYPE intel]
SECTION access_points: mission=<null> problems=[WRONG_TYPE access_points]
EXIT=0
```

Проба защиты в глубину (`Loader._items` на словаре, строке и отсутствующем ключе): `[]`, `[]`, `[]`.

**Уточнение к формулировке находки.** В моём окружении «виснет» воспроизвелось не как
бесконечный цикл процесса: `_process`-сторож `run.gd` ловит аборт `_initialize()` и завершает
процесс кодом 1 за 0.37 с. Но сам дефект воспроизведён дословно: валидатор возвращал `[]`,
загрузчик падал рантаймом ВНУТРИ цикла — то есть «сторож/код возврата» зависели от того, что
ошибка прервёт скрипт, а не от проверки. Разница может быть в способе запуска (голый
`--script` против `--headless --path game --script`, другой раннер/обёртка, повтор ошибки на
каждой итерации). Чинил причину, а не симптом: теперь обе стороны дают детерминированный
результат, и прогон завершается.

**Какие проверки это ловят.** `test_content_validator.gd:117` — цикл по пяти разделам:
`{"guard_1": {...}}` в разделе даёт ровно `WRONG_TYPE` на этом разделе (сравнение списка
кодов, а не «непусто»). `test_content_loader.gd:184` — цикл по пяти разделам: `mission == null`
и `WRONG_TYPE` в проблемах; плюс раздел строкой (`:195`). Зависание проявилось бы таймаутом
самого прогона.

## Решения вопреки брифу (с обоснованием)

1. **`to_int` возвращает `null`, а не проблему.** Бриф: «нечисло — не 0, а **явная проблема**».
   Загрузчик может вернуть проблему только одним способом — не собрать миссию; а `to_int`
   вызывается и из `load_plan`, где проблем нет по контракту («отсутствующие поля — не
   ошибка»). Поэтому явность сделана на уровне значения: `null` — «числа здесь нет», и это
   отличается от честного нуля. Сквозной отказ по-прежнему даёт валидатор (`WRONG_TYPE`), а
   `null`-ветка — защита в глубину, проверяемая шестью кейсами.
2. **`_check_trigger` теперь возвращает словарь `{type, edge}`, а не строку типа.** Нужно было
   донести `trigger.edge` до проверки выполнимости, не читая триггер второй раз и не плодя

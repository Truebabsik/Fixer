# Дизайн: контент-конвейер (загрузка миссии из JSON + валидатор + окна из данных)

Дата: 2026-09-27. Статус: **дизайн, ждёт утверждения.**
Контекст: ядро П1 ([../architecture.md](../architecture.md)), постановка для внешней сессии ([../handoff/2026-09-26-mission-content/](../handoff/2026-09-26-mission-content/)).

---

## 1. Задача и границы

**Что делаем.** Загрузку миссии из JSON, валидатор с различимыми проблемами и перевод окон, их вариантов и эффектов из кода в данные.

**Зачем именно сейчас.** Постановка наружу обещает схему, которую ядро принимать не умеет: форма снята с кода (коммит `6133b60`), но окна, их варианты и эффекты зашиты в `_maybe_open_window` (`sim.gd:342-359`), `WindowScript.locked_door` (`window.gd:8-20`) и `_apply_option`/`_apply_silence` (`sim.gd:424-449`). Без этого конвейера артефакты генератора грузить некуда, и половина уровня молча потеряется.

**Что НЕ делаем:** презентацию, поиск пути, экономику и найм, чтение справочников `spr/` из JSON, замену тестовой фикстуры.

---

## 2. Что выяснилось при сверке с кодом (и меняет объявленную схему)

Три факта, которых не было видно из спецификации и которые правят постановку:

1. **Id окна — составная строка.** `"locked_door:%s" % edge_id` (`window.gd:10`), а не свободный id. В данных миссии окно идентифицируется по `trigger`; составной id остаётся **рантаймовым** ключом, чтобы события и `order()` не менялись.
2. **Цена варианта лежит прямо на варианте** (`noise`, `delay` в `window.gd:16-17`), а не во вложенном `cost`. Схему из постановки приводим к этой форме.
3. **Молчание — не данные, а следствие импровизации.** `_resolve_silence` (`sim.gd:402-420`) смотрит роли живых своих и бросает кубик по seed: `good` — открыть и не платить, `neutral` — задержка 3, `bad` — задержка 3 и шум 5, `safe` — задержка 3. В данных задаётся только **что** происходит при каждом качестве, а **выбор качества** остаётся за ядром (D7).

**Следствие для `reroute`.** В постановке объявлен эффект `reroute` (увести группу через помещение). В ядре такой возможности **нет**: поиска пути в П1 не существует, маршрут — явный список точек (`plan.route`), после цели — прямой отрезок «цель → выход» (§10 architecture, «осознанно за бортом»). Значит `reroute` либо реализуется как новый механизм (поиск пути), либо заменяется честной парой «задержка + открыть ребро». Решение — §5.

## 3. Состав конвейера

| Модуль | Ответственность | Почему отдельный |
|---|---|---|
| `game/content/loader.gd` | Dictionary/JSON → объект `Mission` (+ отдельно `Plan`) через существующий `add_*` | Единственное место, знающее про JSON: типы, отсутствующие поля, приведение чисел. `sim/` остаётся чистым |
| `game/content/validator.gd` | Проблемы с **кодами**: ссылочная целостность, уникальность, осмысленность, достижимость, инварианты окон | `Mission.validate()` возвращает только русские строки (`mission.gd:62-85`) и не покрывает окна и достижимость |
| `game/content/problems.gd` | Формат проблемы `{code, path, message}` и коды строкой | Чтобы вызывающий (тесты, редактор, отчёт прогона) различал причины машинно, а не по тексту |
| `Mission.windows` (+ `intel`, `access_points`) | Новые разделы данных в существующем объекте | `Mission` остаётся **единственной** моделью миссии; никакого второго представления |
| `sim.gd`: `_maybe_open_window`, `order`, `_apply_option` | Читают окна из данных по триггеру | Поведение то же, источник правил — данные |

**Почему не «сырые словари напрямую в Sim».** Тогда `mission.edge()`, `edges_at()`, `edge_between()`, `validate()` и весь `sim/` переписываются, а вместе с ними 259 проверок. Цена выше выгоды: словари не дают ни типов, ни гарантий, а `add_*` уже работают.

**Почему не «всё в `mission.gd`».** Загрузчик JSON и валидатор контента — это `content/`, а не `sim/`: `mission.gd` не должен знать ни про JSON, ни про коды проблем (`architecture.md` §2, слои в одну сторону).

## 4. Схема окна в данных (приведена к фактическому коду)

```json
{
  "id": "w_bio_door",
  "trigger": {"type": "locked_edge", "edge": "e_office_it4"},
  "text_key": "window.w_bio_door.text",
  "options": [
    {"id": "breach", "text_key": "window.w_bio_door.breach", "complexity": 1,
     "noise": 12, "delay": 0, "unlock": true},
    {"id": "pick", "text_key": "window.w_bio_door.pick", "complexity": 2,
     "noise": 1, "delay": 4, "unlock": true}
  ],
  "silence": {
    "text_key": "window.w_bio_door.silence",
    "good": {"unlock": true},
    "neutral": {"delay": 3},
    "bad": {"delay": 3, "noise": 5},
    "safe": {"delay": 3}
  }
}
```

**Инварианты (проверяет валидатор):** вариант с id `silence` запрещён; `silence` обязателен; `complexity` 1–3; `trigger` одного из известных типов; все ссылки существуют; id окна уникален.

**Что остаётся кодом (осознанно):** выбор качества молчания (кубик по seed, D7), пороги эфира, прибытие группы, состояния людей, формула урона. Это законы мира, а не контент уровня.

### 4.1 Одна форма для авторов — вторая внутри ядра

Постановка наружу (§4) держит **семантичную** форму: цена собрана в `cost`, эффекты — массив `effects`, четыре исхода молчания лежат прямо в окне. Ядро же хранит окно в **плоской рантайм-форме**: `noise`/`delay` на варианте (`window.gd:16-17`), молчание — не данные, а качество импровизации, id окна составной.

Это не рассогласование, а разделение: **автор контента не должен знать про рантайм-формат**, а `Sim` не должен разбирать авторскую структуру. Конвертацию делает загрузчик — ровно в одном месте:

| В постановке (для автора) | В ядре (рантайм) |
|---|---|
| `options[].cost.noise`, `cost.delay` | `noise`, `delay` на самом варианте |
| `options[].effects[]` (массив) | применяется по одному эффекту, `_apply_effect` |
| `silence.good/neutral/bad/safe` (массив эффектов) | выбирается качество из `_resolve_silence`, затем берётся соответствующий набор |
| `trigger` | вычисленный id окна `"<kind>:<edge>"` — форма сохранена, чтобы не менять события |

**Следствие для тестов:** эквивалентность проверяется на уровне `Mission` после загрузки, а не на уровне JSON — сравнивать сырые данные с рантайм-формой бессмысленно.

## 5. Решения, требующие утверждения

### 5.1 Что делать с `reroute`

| Вариант | Цена | Последствие |
|---|---|---|
| **A. Заменить на «задержка + unlock»** (рекомендую) | ноль | Честно: ядро делает ровно то, что умеет. Постановка наружу правится: эффект `reroute` объявляется недействительным, `fallback` в `engine_proposal` указывает на `delay`/`unlock` |
| B. Реализовать `reroute` через новый поиск пути | высокая | Открывает целый пласт (П1 его осознанно не делал): придётся решать блокировки, запасной маршрут, поведение патрулей |
| C. Ввести `reroute` как «пропустить оставшиеся waypoints до цели» | средняя | Полупоиск пути: работает для простых графов, врёт на сложных, и это трудно объяснить |

Рекомендация: **A сейчас, B отдельной задачей.** Иначе конвейер тянет за собой подсистему, которой в П1 не было, и артефакты генератора ждут её.

### 5.2 Остаётся ли `add_*` API

Предлагаю **оставить и не трогать**: фикстура `tests/fixtures/small_mission.gd` продолжает собирать миссию кодом, все 259 проверок остаются зелёными, а загрузчик — второй путь. Один тест-кейс проверит, что **оба пути дают одинаковую миссию** (загруженная из JSON эквивалентна собранной кодом) — это и есть защита от расхождения двух путей.

### 5.3 Окна в фикстуре

Фикстура получает **те же определения окон в данных**, что и реальная миссия: иначе data-путь окон не покрыт 259 проверками, и «окна из данных» останутся непроверенными в реальном использовании. Существующие ожидания (`"locked_door"`, `e_office_vault`) сохраняются: составной id остаётся тем же (§2), поэтому правки в тестах минимальны.

### 5.4 Что делать с `Mission.validate()`

Не удалять и не ломать: остаётся как есть (русские строки, используется в `setup`). Новый валидатор — **надстройка** над ней: сначала семантика `sim`-уровня, затем коды `content`-уровня. Дублирование ссылочных проверок допустимо и полезно: они ловят разное (одно — «миссия внутри несогласована», другое — «файл контента неверен, вот где»).

## 6. Порядок работ (каждый шаг — TDD, отдельный коммит)

1. `problems.gd` — формат проблемы и коды. Тест: коды различимы, путь указывает на место.
2. `validator.gd` — проверки по списку из постановки (`02-format.md` §3). Тест: каждая проверка ловит свой дефект (по одному кейсу на код).
3. `loader.gd` — Dictionary → `Mission`: обязательные поля, приведение чисел, неизвестные ключи. Тест: эквивалентность фикстуре; отсутствие поля — проблема с кодом, а не падение.
4. `Mission.windows/intel/access_points` + перенос окон фикстуры в данные. Тест: 259 прежних проверок зелёные, поведение окна не изменилось.
5. Ядро: `_maybe_open_window` читает триггеры из данных; `order`/`_apply_*` применяют эффекты из данных. Тест: все существующие проверки окон и молчания проходят на данных, плюс новый триггер (`node_entered`).
6. Эквивалентность трёх путей: фикстура-код ↔ фикстура-JSON ↔ (позже) миссия генератора.

**Гейт после каждого шага:** `--check-only`, зелёный прогон, красный прогон (код 0).

## 7. Риски

| Риск | Чем закрыт |
|---|---|
| Окна из данных меняют поведение, и 259 проверок этого не замечают | Шаг 4 идёт до шага 5: сначала данные с прежним кодом, потом код на данных. Любое расхождение видно на существующих проверках |
| Схема конвейера разойдётся со схемой постановки | Правки в постановку вносятся тем же коммитом: `cost` → `noise`/`delay`, `reroute` → решение §5.1 |
| Валидатор и `Mission.validate()` начнут противоречить | Разные уровни и разные сообщения; в §5.4 зафиксировано, что дублирование осознанно |
| Неизвестное поле в JSON молча теряется | Загрузчик сообщает неизвестные ключи проблемой с кодом (кроме явно разрешённого `note`) |

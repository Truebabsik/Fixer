# Бриф 10: форма контента под презентацию — координаты, подписи, этажи

Общая часть — `docs/agents/constraints.md` (читается целиком, здесь не дублируется).
Разбор, из которого выросла задача — `docs/current/2026-09-27-mission-01-accept/design-presentation-data.md`.
Кратко в дизайне — `docs/design.md` §25. Контекст — `plan.md` (задача 11).

## Зачем

Экран операции (`docs/current/ui-operation-screen.svg`) рисует схему этажа с подписями помещений, а карту
**нарисовать нечем**: у узла есть только `{floor, tags}`, а `tags` — семантика (`server`, `office`),
не подпись. Названия комплекса и этажей (`МЕРИДИАН // АРХИВНЫЙ КОМПЛЕКС`, `ЭТАЖ 4 // ИТ-ОТДЕЛ`) взять
негде вообще.

Это **форма контента**, и её надо зафиксировать **до** того, как обогащение уровня уедет наружу:
иначе внешний исполнитель сдаст топологию без координат, и её придётся переделывать.

## Что сделать

### A. Поля формы

1. **`nodes[].pos`** — координаты помещения на схеме этажа. Тип: объект `{"x": <int>, "y": <int>}`.
   **Необязательное** поле: уровень без координат обязан оставаться валидным и грузиться (это условие
   приёмки, а не пожелание). Если поле есть — оба ключа обязательны, оба целые; отрицательные
   допускаются (схема может быть с отрицательными координатами).
2. **`nodes[].name_key`** — ключ подписи помещения. Необязательное поле, тип String, если есть.
   Значение — в текстах. Соглашение об именах ключей: **`room.<node_id>`** (например `room.it4`).
3. **`floors`** — новый **необязательный** корневой раздел: `{"<номер этажа>": {"name_key": "floor.<номер>"}}`.
   Ключ — номер этажа **строкой** (в JSON ключи объектов строковые; `-1` для подвала допустим).
   `name_key` внутри — обязателен, если запись есть.
4. **`facility_key`** — необязательное корневое поле String: ключ названия комплекса. Значение
   в текстах (`facility.meridian`).

**Что не является частью задачи:** цвет и стиль помещений, иконки, порядок отрисовки, координаты
этажей на экране (это сетка интерфейса, а не данные уровня). Не добавляй полей «на будущее».

### B. Валидатор

5. Новые поля обязаны проверяться **как известные**: `nodes[].pos` и `nodes[].name_key` — в список
   разрешённых полей узла; `floors` и `facility_key` — в корневые. Иначе они дадут `UNKNOWN_KEY`
   на любой миссии, которая их использует.
6. **Типы проверяются по факту поля** (тот же принцип, что у `trace_key`): `pos` — объект с целыми
   `x`/`y`; `name_key`, `facility_key`, `floors[].name_key` — строки. Не-строка в ключе текста — 
   `WRONG_TYPE` на своём пути, и он собирается тем же обходом `*_key`, что и остальные (проверь это
   ассертом, а не предположением).
7. `floors` — **не** раздел-массив: это словарь. Проверь форму отдельно: не словарь → `WRONG_TYPE`;
   запись не словарь → `WRONG_TYPE` на своём пути; нет `name_key` → `MISSING_FIELD`.
8. Проверь, что новый необязательный раздел **не ломает** правило «разделы-массивы обязательны»:
   `floors` обязательным быть не должен, и его отсутствие не даёт проблем.
9. Сверка текстов идёт в обе стороны как прежде: ключ из `name_key`/`facility_key`, которого нет
   в текстах, — `MISSING_TEXT`; лишний ключ семейств `room.`/`floor.`/`facility.` — `DANGLING_TEXT`.
   Если для этого нужно расширить `UNUSED_OK_PREFIXES` — **не расширяй**: эти ключи выводятся из данных,
   и они обязаны быть привязаны к данным.

### C. Данные первой миссии

10. **Заполни новые поля для `game/content/mission-01.json`** — иначе форма останется непроверенной
    на реальном контенте:
    - `pos` для **всех 28** помещений: координаты должны соответствовать **смыслу** здания, а не быть
      случайными. Ориентир — `levels/mission-01.md` (этажи и связи) и `docs/design.md` §19: **три
      вертикальные связи** (пассажирский лифт, грузовой лифт, лестница) должны читаться на схеме как
      три разных пути, а не как одна линия. Помещения одного этажа не должны наезжать друг на друга:
      проверь расстояния и назови в отчёте, по какому шагу сетки раскладывал.
    - `name_key` для всех узлов, у которых есть **осмысленное** имя (комнаты, терминалы, лифты,
      лестницы, кровля), и тексты `room.*` для них;
    - `facility_key` + тексты `facility.meridian`; `floors` с `name_key` для этажей **−1…6** и текстами
      `floor.*`.
11. Тексты пиши по `docs/spr/text-style.md` и `04-texts.md` §2: это **подписи на схеме** (короткие
    существительные), а не реплики. Названия этажей — как на макете: `ЭТАЖ 4 // ИТ-ОТДЕЛ`.
12. **Координаты не влияют на симуляцию.** Проверь и докажи пробой: прогон с координатами и без них
    даёт **тот же** `harness.digest` (координаты — данные для отображения; ядро их не читает).

### D. Кейс

13. Сценарии в существующих кейсах (новых файлов не заводить, `.uid` за ведущим):
    - миссия **без** `pos`/`floors`/`facility_key` — валидатор чист, миссия собирается (обратная
      совместимость формы);
    - миссия **с** ними — валидатор чист и ключи `room.*`/`floor.*`/`facility.*` сходятся с текстами;
    - `pos` = `{"x": "5"}` (строка вместо числа) → `WRONG_TYPE` на своём пути;
    - `name_key` = `5` → `WRONG_TYPE`, и **кейс не теряет ассерты** (урок F1 ревью 2);
    - `floors` = `[]` (массив вместо словаря) → `WRONG_TYPE`;
    - ключ `room.*` в текстах без узла в данных → `DANGLING_TEXT`.
    Каждый сценарий — своя мутационная проба с **именем** ассерта.

### E. Чего не делать

- Не менять `sim/` — координаты ядру не нужны; `Mission.nodes` может их хранить, но не обязан, если
  ты решишь оставить их только в `data` (реши и обоснуй).
- Не трогать топологию уровня (маршруты, рёбра, окна) — ревизия топологии отдельная задача наружу.
- Не править `docs/**` — формулировку для `architecture.md` и `design.md` назови в отчёте, допишет ведущий.
- Не трогать `levels/mission-01-content/**` и `docs/handoff/**`.

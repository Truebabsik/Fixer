## 1. Стек

| | |
|---|---|
| Движок | **Godot 4.7.2 stable** (win64), лежит в `tools/Godot_v4.7.2/` |
| Язык | GDScript |
| Размерность | 2D |
| Платформа | PC, клавиатура + мышь |
| Данные | JSON (контент миссий, справочники) |
| Проект | `game/` (там `project.godot`) |

**Почему GDScript.** Нет ни одного места, где нужна производительность: симуляция — это граф из десятков узлов и несколько десятков шагов. Плавность даёт презентация (анимация иконок), а не расчёт. GDScript быстрее итерируется, и весь проект остаётся в одном языке.

**Почему JSON, а не Godot Resource.** Контент миссий должен быть читаемым и diff-абельным в текстовом виде: окна решений, реплики, расписания патрулей, даты разведданных. Ресурсы удобны в редакторе, но плохо смотрятся в системе контроля версий и провоцируют редактирование через GUI вместо текста. JSON + валидатор на старте загрузки — предсказуемее.

## 2. Слои

Три слоя, зависимости строго в одну сторону:

```
content (данные)  →  sim (логика)  →  presentation (рендер/UI)
                        ↑
                    tests (проверка, headless)
```

### 2.1 `sim` — ядро симуляции · **реализовано**
**Чистая логика. Не знает о рендере, сценах, `Node`, вводе и времени кадра.** Знает только: граф комнат, двери, сенсоры, агентов, шкалы, окна решений, пул приказов.

- Вход: определение миссии (данные) + план игрока + последовательность ответов на окна.
- Выход: поток событий (§5) + финальное состояние (`result()`).
- **Не мутирует ничего в презентации и не читает оттуда.**
- Прогонщик сценариев `sim/harness.gd` — не отдельный слой, а часть ядра: ещё один потребитель `Sim`, который крутит окна и собирает отпечаток исхода.

### 2.2 `content` — данные · **реализовано (конвейер)** · первая миссия — на приёмке
Комнаты, двери, точки доступа, камеры, маршруты патрулей, расписания, «призраки» из разведки, окна решений, реплики, числа экономики. Конвейер из JSON реализован тремя модулями:

| Модуль | Назначение |
|---|---|
| `content/problems.gd` | одна форма проблемы на весь конвейер: код, путь в файле контента, сообщение; фабрики (`MISSING_FIELD`, `BAD_REF`, `UNWINNABLE_EDGE`, …) |
| `content/validator.gd` | проверка ФАЙЛА: типы, неизвестные ключи, дубли, ссылки, достижимость, инварианты окон. Ничего не чинит и не бросает: на любой дефект — проблема в списке |
| `content/loader.gd` | словарь или строка JSON → модель `sim/mission.gd`. Правило «сначала валидатор, потом сборка»: негодный словарь миссии не даёт вовсе |

Миссии для тестов по-прежнему собираются кодом (`tests/fixtures/`) — это второй, независимый путь к той же модели, и его совпадение с конвейером проверяется (`test_content_loader.gd`).

**Форма данных зафиксирована** в постановке для внешней сессии: [`docs/handoff/2026-09-26-mission-content/02-format.md`](handoff/2026-09-26-mission-content/02-format.md). Схема снята из кода и разделена на два уровня: **A** — то, что ядро читает уже сейчас (`nodes`, `edges`, `patrols`, `sensors`, `objective`); **B** — объявленное расширение (`windows`, `intel`, `access_points`), конвейер под которое написан. Ключевой факт, из которого это выросло: в П1 окна, их варианты и эффекты **зашиты в код** (`sim.gd:_maybe_open_window`, `window.gd:locked_door`, `sim.gd:_apply_option`), поэтому контент уровня без расширения ядра принять нечем.

Образец формы (`example-mission.skeleton.json`, тот же пакет) прогоняется нашим валидатором в автотесте `tests/cases/test_handoff_skeleton.gd`: ноль проблем и собранная миссия. Обещание README пакета «скелет проходит наш валидатор» стало проверяемым, а не словом.

**Контракт текстов — выбор вызывающего, а не умолчание.** `Validator.validate(data, texts)`, `Loader.load_mission(data, texts)` и `Loader.load_text(json_text, texts)` требуют второй аргумент **без значения по умолчанию**. Три состояния: `null` — сверка ключей не выполняется (явный отказ); словарь (в том числе пустой) — выполняется, где пустой означает «текстов нет», и тогда каждый `*_key` из данных считается отсутствующим; **значение иного типа — ошибка контракта**. Зачем так: с умолчанием `{}` вызов без текстов **молча пропускал** сверку, и вызывающий, забывший тексты, получал «проблем нет»; обязательный аргумент делает забывание ошибкой компиляции, а `null` в коде читается как решение. Тип проверяется явно: подстановка строки или числа (правдоподобная у `load_text`, где рядом два строковых параметра) даёт проблему, а не «ноль проблем» — иначе дыра «выглядеть успешным, ничего не проверив» осталась бы открытой. Тот же класс, что ложные ворота `--check-only` (§8).

**`unlock` — одно понятие на замок и на тревогу.** Ребро бывает непроходимо двумя способами: `locked` в данных и тревога (`Response.edge_blocked`, §5). Прежде это были два независимых запрета с одним исходом (`continue`), и снять тревожную блокировку было **нечем**: `unlock` писал в `unlocked`, который читал только замок. Теперь одна функция `sim.gd:_is_blocked_for` отвечает на вопрос «не может ли ЭТОТ агент пройти по ЭТОМУ ребру сейчас» и используется **в двух местах** — запрет шага (`_advance_own`) и выбор актора окна (`_actor_before_locked_edge`). Второе условие здесь и было дефектом: актор выбирался по `_is_locked`, поэтому окно у ребра, перекрытого тревогой, **не открывалось ни разу** — данные сцену описывали, а сцены не было. Замок и тревога держат по-разному, и это не небрежность: замок — при любом `progress` (дверь не отпереть на ходу), тревога — только на старте перехода (`progress == 0`): лифт, который уже поехал, назад не отзывают, иначе игрок наказан за то, чего не мог предвидеть. Одна запись в `unlocked` снимает **оба** запрета, и снимает **именно это** ребро (по id, не по виду): соседний лифт того же вида остаётся перекрытым.

**«Ребро запираемо» = замок ИЛИ тревога — и список видов один на проект.** Окно с триггером `locked_edge` законно не только на запертом ребре, но и на ребре, которое перекрывает тревога (`WINDOW_ON_OPEN_EDGE` — только для ребра, которое не запирается ничем). Виды, перекрываемые тревогой, живут **в одном месте** — `sim/response.gd:BLOCKED_KINDS`; `edge_blocked` и валидатор (`Response.blockable_kind`) читают один список. Второй перечень у валидатора разошёлся бы с ядром молча — тот же класс, что `TRIGGER_TYPES`/`WINDOW_KINDS`, но через границу «контент ↔ ядро», и заметить расхождение было бы нечем: валидатор и прогон смотрели бы на разные списки.

**`trace_key` у точки доступа** — необязательное поле String (`04-texts.md` §3.4): ключ сухой строки о следе для «Итогов». Собирается тем же обходом `*_key`, что и остальные текстовые ключи, поэтому `ap.<id>.trace` перестаёт быть висячим; тип проверяется явно.

**Типы текстовых `*_key` проверяются, и каскад диагнозов назван прямо.** Не-строка в любом текстовом поле (`title_key`, `windows[].text_key`, `options[].text_key`, ключи качеств молчания, `access_points[].text_key`/`trace_key`, `actions[].text_key`, `intel[].entries[].note_key`) даёт `WRONG_TYPE` **на своём пути**. **Испорченное поле остаётся не-строкой и для сверки текстов**, поэтому на тот же дефект выходит **второй** диагноз — `DANGLING_TEXT` про текст, который автор не терял: одно испорченное поле = `WRONG_TYPE` + `DANGLING_TEXT`. Это записано как **факт**, а не как желаемое: первая редакция комментария в `validator.gd` утверждала, что проверка типа даёт `WRONG_TYPE` **вместо** `DANGLING_TEXT`, и это было ложью (поймано пробой на ревью). Каскад осознанно **оставлен**: гашение парного диагноза — общее поведение валидатора («одна ошибка — одно следствие»), и вводить его ради одного поля значило бы расширять правку; выбранный компромисс — честный комментарий и **оба** диагноза под ассертом.

**Текст молчания — по выбранному качеству, и выбирает его ядро.** Кто решает за игрока, определяет **не контент**: есть живой связист — импровизирует он, и кубик (единственный в игре, D7) даёт `good`/`neutral`/`bad`; связиста нет — решает тактик, и исход всегда `safe`. Поэтому форма несёт **пять** ключей: базовый `silence.text_key` (что произошло вообще) и `<quality>_key` на каждый из четырёх исходов. Ключ качества — запасной путь: отсутствующее поле даёт пустую строку, а не пропуск, и тогда читается базовый ключ; ключа нет и там — пустая строка (ядро на неполных данных не падает — то же правило, что у пустого списка эффектов). Выбранное качество видно потребителю текста: `Sim.order("silence")` возвращает `text_key` выбранного исхода, а `WindowScript.silence_key_for(w, quality)` даёт ключ по качеству. **Следствие, названное прямо:** при **штатном составе** (Кира-тактик + Эхо-связист) исход `safe` не выпадает **никогда** — это ветка «связиста нет», и всё, что положено только в `safe`, на штатном составе не играется (см. D41).


### 2.3 `presentation` — отображение · **не начато**
Читает события ядра и рисует: карту, иконки, зоны сенсоров, строку «КОМАНДУЕТ: …», планшет, базу, «Итоги». **Никогда не меняет состояние симуляции напрямую.** Единственный способ повлиять на мир — отдать приказ через `Sim.order()`.

### 2.4 `tests` — проверка · **реализовано**
Headless-прогон по сценарию и ассерты на исход. Вердикт — код возврата процесса (§8). Это главный инструмент балансировки и единственный автотест проекта.

## 3. Модель времени

Симуляция продвигается **дискретными шагами** (beat), а не покадрово.

- Шаг = один атомарный отрезок: агент проходит ребро графа, патруль доходит до узла, сенсор обновляется.
- Презентация сама интерполирует движение иконок между шагами. Логика не знает о времени кадра.
- **Автопауза** — это остановка продвижения шагов по событию `window_opened`. Симуляция замирает целиком; пока окно открыто, шагов нет.
- Пул приказов тратится только через окно. «Молчать» — валидный ответ окна, он закрывает окно без списания приказа.

Следствие: **никаких таймеров и `delta` в логике.** Это делает прогон детерминированным и воспроизводимым.

## 4. Детерминизм

Требование, а не пожелание: миссия, переигранная с тем же планом и теми же приказами, обязана дать тот же исход. Иначе `harness` бесполезен, а обещание «ошибка обучаема» — ложь.

Правила:

1. Обход коллекций — в фиксированном порядке (сортировка по id, никогда по порядку в словаре).
2. Единственный источник случайности — RNG импровизации. Он создаётся с сохранённым seed, который пишется в лог прогона.
3. Никаких вызовов, зависящих от реального времени или кадра.
4. Разрешение любого действия — чистая функция от состояния. Случайность влияет только на *выбор действия* агентом при импровизации (см. design.md §13.6).

## 5. Шина событий

Ядро не вызывает презентацию — оно публикует события через `_emit(type, data)`. **Фактический набор** (проверен по `game/sim/`, это то, на что подписывается П2):

| Событие | `data` | Смысл |
|---|---|---|
| `invalid_mission` | `problems` | вход не прошёл валидацию; миссия не началась |
| `mission_started` | `node` | группа на старте |
| `agent_moved` | `agent`, `node`, `edge`, `noise` | свой прошёл ребро (шум уже добавлен) |
| `guard_moved` | `agent`, `node` | охрана шагнула по патрулю |
| `sensor_contact` | `agent`, `node` | охрана вошла в зону сенсора — по фронту, не каждый шаг |
| `ghost_mismatch` | `agent`, `ghost`, `real` | призрак разошёлся с реальностью — момент ужаса |
| `path_blocked` | `agent`, `edge`, `kind` | тревога перекрыла путь |
| `alarm_raised` | `step` | шум перевалил порог: перелом |
| `window_opened` | `kind`, якорь, `agent` | сбой или запрос; автопауза. Якорь — по виду триггера: `edge` у `locked_edge`, `node` у `node_entered`, `sensor` у `guard_in_sensor` (`sim.gd:_window_event_data`). У запертого ребра набор полей прежний |
| `order_issued` | `window`, `option`, `radio` | приказ отдан, списан, ушёл в эфир |
| `order_silenced` | `window`, `effect` | игрок промолчал; решал именной |
| `order_refused` | `window`, `reason` | отказ: `no_orders` / `jammed` / `unknown_option` / `finished` |
| `agent_compromised` | `agent`, `state`, `triggers` | своего засекли: триггер накоплен |
| `objective_reached` | `agent`, `node` | цель взята, группа разворачивается на выход |
| `mission_ended` | `outcome` | `extracted` / `caught` / `timeout` / `invalid_mission` |

Презентация подписывается на события; добавление нового события не требует правки ядра. `Sim.events` — журнал прогона, и он же отчёт для разбора «почему так вышло». **Осторожно:** `Harness.run_scenario` журнал не возвращает (даёт только исход и отпечаток) — если он нужен, брать его из самого `Sim`.

## 6.1 Соглашения кода (выведены на П1, проверены движком)

Это перенесено сюда из плана П1, который уехал в `docs/archive/`, — правила обязательные, а план больше не под рукой.

1. **Вердикт — код возврата процесса.** `quit(0)` зелёный, `quit(1)` провал, `quit(2)` сломан приговор (§8). **Текст в stderr вердиктом не является:** Godot пишет туда безобидный шум (`user://logs/...`, чтение корневых сертификатов) даже при коде 0.
2. **Никаких `class_name` в `game/sim/` и `game/tests/`.** Только `const X := preload("res://...")`. `class_name` не резолвится в headless-прогоне, пока редактор не обновит кэш глобальных классов, — а `preload` резолвится всегда.
3. **Имя константы `preload` не должно совпадать с классом движка.** `const Window := preload(...)` — **жёсткая ошибка разбора** (`shadows a native class`). Поэтому модуль окна подключён как `WindowScript`.
4. **Типизация объектов.** Объекты, созданные прямо из `preload`-константы, — через `:=` (`var s := Scales.new()`): с обычным `=` переменная выходит нетипизированной, и последующий `var x := s.field` не компилируется. Объекты из функций **без аннотации возврата** (фикстура `Fixture.build()`, тестовые хелперы) — через `=` и динамический доступ; аннотировать их возврат нельзя, иначе перестанет компилироваться доступ к членам. Из такого объекта типизированный локальный получать явным типом: `var before: int = sim.scales.step`.
5. **`sim/` не знает о нодах.** Только `RefCounted`: ни `Node`, ни `SceneTree`, ни сцен, ни рендера. Единственные исключения — `tests/run.gd` и `tests/run_red.gd`, потому что `--script` требует `SceneTree`.
6. **Детерминизм.** Обход списков в порядке следования, рёбра — через id-сортированный `edges_at`, никогда не полагаться на порядок словаря. Единственный источник случайности — `rng`, засеянный из `config.seed`; в П1 он используется ровно в одном месте (импровизация именного, D7).
7. **Отступы — табы.** Идентификаторы английские, комментарии и имена тестов русские.
8. **Гейт — `failed: 0`, а не общее число проверок.** Число растёт с каждым кейсом, и в ожиданиях его фиксировать нельзя.

## 7. Правила контента и баланса

1. **Никаких магических чисел в коде.** Все константы (цена канала, гонорар, пороги шума, лечение, цена тела, размер пула приказов) — в одном справочнике `docs/spr/scales.md` и в одном JSON-файле баланса. Балансировка не должна требовать чтения кода.
2. **Тексты отдельно от кода.** Реплики и строки — по ключам, в файлах контента. Стайлгайд — `docs/spr/text-style.md`.
3. **Миссия — это данные.** Добавление второй миссии не должно трогать `sim/`.
4. **Валидация на загрузке.** Контент миссии проверяется на старте: недостижимые комнаты, окна без варианта «молчать», призраки без расписания, ссылки на несуществующие реплики.

## 8. Проверка

**Команды (проверены у бинарника `tools/Godot_v4.7.2/`, не по документации):**

```powershell
# Разбор всех скриптов конвейера без запуска тестов — ворота для каждого изменения
tools\Godot_v4.7.2\Godot_v4.7.2-stable_win64_console.exe --headless --path game --script res://tests/preflight.gd

# Прогон тестов: скрипт сам завершает процесс, код возврата = вердикт
tools\Godot_v4.7.2\Godot_v4.7.2-stable_win64_console.exe --headless --path game --script res://tests/run.gd

# Прогон сцены с гарантированным выходом (без главной сцены движок не выходит сам)
tools\Godot_v4.7.2\Godot_v4.7.2-stable_win64_console.exe --headless --path game --quit-after 600
```

`--quit-after <N>` завершает процесс после N итераций — это лечит таймаут пустого проекта.

**Ворота разбора — `tests/preflight.gd`, а не `--check-only`.** `--check-only --script <файл>` разбирает только названный скрипт и то, что он тянет статическими `preload`. Кейсы и модули конвейера попадают в прогон динамически (`load(path)` в `tests/suite.gd`), поэтому по документированной прежде команде `--check-only --script res://tests/run.gd` синтаксическая ошибка в `game/content/validator.gd` дала код 0 при полностью нерабочем прогоне (проверено 2026-09-27). Одиночный файл — тоже не замена: на том же сломанном дереве `--check-only --script res://tests/cases/test_content_loader.gd` вернул 0, уже напечатав `Parse Error: Could not preload resource script`. Поэтому `preflight.gd` называет пути явно (все модули `sim/` и `content/` плюс `suite.gd.CASES`), а вердикт отдаёт кодом возврата: 0 — разобрались все, 1 — провалившиеся названы строками `LOAD FAIL`.

**Проверка красного пути.** Две команды прогонять вместе: нормальный прогон обязан дать код 0, а нарочно красный — тоже код 0, но по другой причине.

```powershell
# Нормальный прогон: ожидаем "failed: 0" и код 0
tools\Godot_v4.7.2\Godot_v4.7.2-stable_win64_console.exe --headless --path game --script res://tests/run.gd

# Красный путь: ожидаем "red-path: tests: 2, failed: 1" и код 0
tools\Godot_v4.7.2\Godot_v4.7.2-stable_win64_console.exe --headless --path game --script res://tests/run_red.gd
```

**Коды возврата — три, а не два** (`tests/verdict.gd`):

| Код | Зелёный вход | Красный вход |
|---|---|---|
| **0** | набор прошёл | обе проверки красного пути прошли |
| **1** | набор упал | — |
| **2** | приговор сломан: пустой набор или провалы вместо ожидаемых | приговор сломан |

Разделение 1 и 2 не косметика: «упал тест» и «сломан приговор» требуют разных действий, а из одного кода 1 их не различить.

**Как устроена защита приговора.** Считать и приговаривать умеет один модуль — `tests/verdict.gd`, им пользуются оба входа; список кейсов тоже один — `tests/suite.gd`. Сам по себе общий модуль ещё ничего не защищает: если его сломать, оба входа сломаются согласно. Поэтому `run_red.gd` дополнительно выполняет `Verdict.verify()` — две независимые проверки:

1. **Нарочно падающий список, поданный прямо в `evaluate`, обязан дать провал.** Это не проходит через `suite.gd`, поэтому ловит саботаж в самом приговоре.
2. **Зелёный набор при запуске из красного пути обязан пройти.** Это ловит саботаж в зелёном входе: зашитый `quit(0)` в `run.gd` вернёт в эту проверку код 2, и красный прогон упадёт.

Обе проверки понадобились не по рассуждению, а по прогону: **первая редакция защиты ловила саботаж только в раннере.** Когда приговор подменили так, чтобы он игнорировал результаты, красный прогон вернул 0 и промолчал — потому что проверял зелёный набор через тот же сломанный модуль. Проверка «напрямую в `evaluate`» закрывает именно эту дыру.

`run_red.gd` намеренно не имеет `_process`-сторожа: сторож зелёного входа — часть проверяемой системы, и второй его экземпляр ничего не доказывает. `tests/red_path.gd` не входит в список `CASES` нормального прогона — иначе набор всегда был бы красным.

> **Что проверено прогоном (мутационные пробы 2026-09-27).** Подмена тела `evaluate` на «всегда чистый приговор»: зелёный прогон даёт код 0 (саботаж не виден — так и должно быть), красный даёт **код 2** и печатает `BROKEN  приговор не увидел провал`. Зашивание нуля в `suite.run`: красный даёт **код 2**. В прежней редакции обе пробы давали «предписанные коды». Границы честности: детектор живёт в том же процессе и на том же коде, что и защищаемое, поэтому систематическая ошибка в самом `verify()` останется незамеченной — её, в свою очередь, покрывает юнит-тест `cases/test_verdict.gd` в обычном прогоне.

**Что проверяем:**

- **Автотесты исходов (главное).** Сценарии вида «план Б + 3 приказа → ожидаем: задача выполнена, 1 ранение, 0 смертей». Прогоняются headless.
- **Инварианты.** Смерть невозможна при нуле накопленных ошибок; пул приказов не уходит в минус; окно всегда содержит «молчать»; при молчании на всей миссии никто не погибает.
- **Проверка сцен в редакторе.** Через Godot MCP: дерево сцены, свойства узлов, пробный headless-запуск сцены.
- **Ручная проверка тона** — не автоматизируется. Читать вслух.

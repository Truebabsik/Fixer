## 1. Стек

| | |
|---|---|
| Движок | **Godot 4.7.2 stable** (win64), лежит в `tools/Godot_v4.7.2/` |
| Язык | GDScript |
| Размерность | 2D |
| Платформа | PC, клавиатура + мышь |
| Данные | JSON (контент миссий, справочники) |
| Проект | `game/` (там `project.godot`) |
| IDE-связка | MCP-мост: аддон `godot_mcp` в проекте ↔ сервер `godot-mcp` (см. §9) |

**Почему GDScript.** Нет ни одного места, где нужна производительность: симуляция — это граф из десятков узлов и несколько десятков шагов. Плавность даёт презентация (анимация иконок), а не расчёт. GDScript быстрее итерируется, и весь проект остаётся в одном языке.

**Почему JSON, а не Godot Resource.** Контент миссий должен быть читаемым и diff-абельным в текстовом виде: окна решений, реплики, расписания патрулей, даты разведданных. Ресурсы удобны в редакторе, но плохо смотрятся в системе контроля версий и провоцируют редактирование через GUI вместо текста. JSON + валидатор на старте загрузки — предсказуемее.

## 2. Слои

Четыре слоя, зависимости строго в одну сторону:

```
content (данные)  →  sim (логика)  →  presentation (рендер/UI)
                          ↓
                      harness (headless-прогоны, автотесты)
```

### 2.1 `sim` — ядро симуляции
**Чистая логика. Не знает о рендере, сценах, `Node`, вводе и времени кадра.** Знает только: граф комнат, двери, сенсоры, агентов, шкалы, окна решений, пул приказов.

- Вход: определение миссии (данные) + план игрока + последовательность приказов.
- Выход: поток событий + финальное состояние.
- **Не мутирует ничего в презентации и не читает оттуда.**

### 2.2 `content` — данные
Комнаты, двери, точки доступа, камеры, маршруты патрулей, расписания, «призраки» из разведки, окна решений, реплики, числа экономики. Всё, что может изменить геймдизайнер без правки логики.

### 2.3 `presentation` — отображение
Читает события ядра и рисует: карту, иконки, зоны сенсоров, строку «КОМАНДУЕТ: …», планшет, базу, «Итоги». **Никогда не меняет состояние симуляции напрямую.** Единственный способ повлиять на мир — отправить в ядро приказ.

### 2.4 `harness` — проверка
Headless-прогон миссии по сценарию: `{план, последовательность приказов}` → `{исход, шкалы, ранения, смерти, потраченные приказы}`. Это главный инструмент балансировки и главный автотест проекта.

## 3. Модель времени

Симуляция продвигается **дискретными шагами** (beat), а не покадрово.

- Шаг = один атомарный отрезок: агент проходит ребро графа, патруль доходит до узла, сенсор обновляется.
- Презентация сама интерполирует движение иконок между шагами. Логика не знает о времени кадра.
- **Автопауза** — это остановка продвижения шагов по событию `window_opened`. Симуляция замирает целиком; пока окно открыто, шагов нет.
- Пул приказов тратится только через окно. «Молчать» — валидный ответ окна, он закрывает окно без списания приказа.

Следствие: **никаких таймеров и `delta` в логике.** Это делает прогон детерминированным и воспроизводимым.

---

## 4. Детерминизм

Требование, а не пожелание: миссия, переигранная с тем же планом и теми же приказами, обязана дать тот же исход. Иначе `harness` бесполезен, а обещание «ошибка обучаема» — ложь.

Правила:

1. Обход коллекций — в фиксированном порядке (сортировка по id, никогда по порядку в словаре).
2. Единственный источник случайности — RNG импровизации. Он создаётся с сохранённым seed, который пишется в лог прогона.
3. Никаких вызовов, зависящих от реального времени или кадра.
4. Разрешение любого действия — чистая функция от состояния. Случайность влияет только на *выбор действия* агентом при импровизации (см. design.md §13.6).

## 5. Шина событий

Ядро не вызывает презентацию — оно публикует события. Минимальный набор:

| Событие | Смысл |
|---|---|
| `step_completed` | прошёл шаг симуляции |
| `agent_moved` | агент переместился по ребру |
| `sensor_contact` | агент попал в зону сенсора |
| `ghost_mismatch` | призрак разошёлся с реальностью — момент ужаса |
| `window_opened` | сбой или запрос подтверждения; автопауза |
| `order_issued` | приказ отдан; списан из пула |
| `order_misunderstood` | биржевик исполнил буквально |
| `agent_improvising` | Эхо действует сам (единственная случайность) |
| `noise_changed` / `time_changed` / `agent_state_changed` | движение шкал |
| `agent_injured` / `agent_dead` | последствия |
| `mission_ended` | исход |

Презентация подписывается на события; добавление нового события не требует правки ядра. События логируются — лог прогона и есть отчёт `harness`.

## 6.1 Соглашения кода (выведены на П1, проверены движком)

Это перенесено сюда из плана П1, который уехал в `docs/archive/`, — правила обязательные, а план больше не под рукой.

1. **Вердикт — код возврата процесса.** `quit(0)` зелёный, `quit(1)` провал. **Текст в stderr вердиктом не является:** Godot пишет туда безобидный шум (`user://logs/...`, чтение корневых сертификатов) даже при коде 0.
2. **Никаких `class_name` в `game/sim/` и `game/tests/`.** Только `const X := preload("res://...")`. `class_name` не резолвится в headless-прогоне, пока редактор не обновит кэш глобальных классов, — а `preload` резолвится всегда.
3. **Имя константы `preload` не должно совпадать с классом движка.** `const Window := preload(...)` — **жёсткая ошибка разбора** (`shadows a native class`). Поэтому модуль окна подключён как `WindowScript`.
4. **Типизация объектов.** Объекты, созданные прямо из `preload`-константы, — через `:=` (`var s := Scales.new()`): с обычным `=` переменная выходит нетипизированной, и последующий `var x := s.field` не компилируется. Объекты из функций **без аннотации возврата** (фикстура `Fixture.build()`, тестовые хелперы) — через `=` и динамический доступ; аннотировать их возврат нельзя, иначе перестанет компилироваться доступ к членам. Из такого объекта типизированный локальный получать явным типом: `var before: int = sim.scales.step`.
5. **`sim/` не знает о нодах.** Только `RefCounted`: ни `Node`, ни `SceneTree`, ни сцен, ни рендера. Единственные исключения — `tests/run.gd` и `tests/run_red.gd`, потому что `--script` требует `SceneTree`.
6. **Детерминизм.** Обход списков в порядке следования, рёбра — через id-сортированный `edges_at`, никогда не полагаться на порядок словаря. Единственный источник случайности — `rng`, засеянный из `config.seed`; в П1 он используется ровно в одном месте (импровизация именного, D7).
7. **Отступы — табы.** Идентификаторы английские, комментарии и имена тестов русские.
8. **Гейт — `failed: 0`, а не общее число проверок.** Число растёт с каждым кейсом, и в ожиданиях его фиксировать нельзя.

## 7. Правила контента и баланса

1. **Никаких магических чисел в коде.** Все константы (цена канала, гонорар, пороги шума, лечение, цена тела, размер пула приказов) — в одном справочнике `docs/spr/scales.md` и в одном JSON-файле баланса. Балансировка не должна требовать чтения кода.
2. **Тексты отдельно от кода.** Реплики и строки — по ключам, в файлах контента. Стайлгайд — `docs/spr/text-style.md`.
3. **Миссия — это данные.** Добавление второй миссии не должно трогать `sim/`.
4. **Валидация на загрузке.** Контент миссии проверяется на старте: недостижимые комнаты, окна без варианта «молчать», призраки без расписания, ссылки на несуществующие реплики.

## 8. Проверка

**Команды (проверены у бинарника `tools/Godot_v4.7.2/`, не по документации):**

```powershell
# Быстрый разбор без запуска — ворота для каждого изменения
tools\Godot_v4.7.2\Godot_v4.7.2-stable_win64_console.exe --headless --path game --check-only --script res://tests/run.gd

# Прогон тестов: скрипт сам завершает процесс, код возврата = вердикт
tools\Godot_v4.7.2\Godot_v4.7.2-stable_win64_console.exe --headless --path game --script res://tests/run.gd

# Прогон сцены с гарантированным выходом (без главной сцены движок не выходит сам)
tools\Godot_v4.7.2\Godot_v4.7.2-stable_win64_console.exe --headless --path game --quit-after 600
```

`--quit-after <N>` завершает процесс после N итераций — это лечит таймаут пустого проекта. `--check-only` парсит и выходит: дешёвые ворота, которые ловят синтаксис до прогона.

**Проверка красного пути.** Две команды прогонять вместе: нормальный прогон обязан дать код 0, а нарочно красный — код 1.

```powershell
# Нормальный прогон: ожидаем "failed: 0" и код 0
tools\Godot_v4.7.2\Godot_v4.7.2-stable_win64_console.exe --headless --path game --script res://tests/run.gd

# Красный путь: ожидаем "red-path: tests: 2, failed: 1" и код 1
tools\Godot_v4.7.2\Godot_v4.7.2-stable_win64_console.exe --headless --path game --script res://tests/run_red.gd
```

`run_red.gd` намеренно не имеет `_process`-сторожа: его задача — показать, что падающая проверка валит процесс, а не повторить сторожа нормального раннера. `tests/red_path.gd` не входит в список `CASES` нормального прогона — иначе набор всегда был бы красным.

> **Чего эта пара НЕ делает (проверено ревью, исправлено в тексте).** `run_red.gd` — **отдельная копия** логики раннера, и его код возврата жёстко равен 1 независимо от результата. Поэтому он **не** защищает от зашитого `quit(0)` в `run.gd`: такой саботаж оставит оба прогона в предписанных кодах. Настоящая защита требует, чтобы подсчёт и приговор жили в **общем** модуле, которым пользуются оба входа, и чтобы красный прогон возвращал 0, если нарочная ошибка не была зафиксирована. Это задача следующего этапа; до тех пор опираться на эту пару как на защиту приговора нельзя.

**Что проверяем:**

- **Автотесты исходов (главное).** Сценарии вида «план Б + 3 приказа → ожидаем: задача выполнена, 1 ранение, 0 смертей». Прогоняются headless.
- **Инварианты.** Смерть невозможна при нуле накопленных ошибок; пул приказов не уходит в минус; окно всегда содержит «молчать»; при молчании на всей миссии никто не погибает.
- **Проверка сцен в редакторе.** Через Godot MCP: дерево сцены, свойства узлов, пробный headless-запуск сцены.
- **Ручная проверка тона** — не автоматизируется. Читать вслух.

**Состояние на 2026-09-26.** 11 кейсов, 229 проверок, `failed: 0`, код возврата 0. Ядро П1 реализовано одиннадцатью задачами по плану `docs/archive/2026-09-26-plan-p1-sim-core.md`; каждую задачу писал отдельный исполнитель, каждую проверяло отдельное ревью, финальное ревью прошло по всей ветке. Ход исполнения, все решения контролёра и ~50 отложенных минорных находок — в леджере `.superpowers/sdd/plan-p1-sim-core/progress.md` (вне git по `.gitignore`).

## 9. Тулчейн и MCP-мост

**Как это устроено.** Направление связи: **аддон подключается наружу**, а не сервер внутрь. Внутри редактора живёт WebSocket-**клиент** (`addons/godot_mcp/mcp_bridge.gd`), который сам зовёт серверный листенер на `ws://127.0.0.1:9080` и переподключается с задержкой 0.5 → 5 с. Поэтому **порядок запуска не важен**: редактор можно открыть до сервера и после.

**Что уже готово:**

- Сервер `godot-mcp 2026.09.23` запускается вместе с DSH и слушает порт 9080.
- Аддон лежит в репозитории: `addons/godot_mcp/`.
- Проект: `game/project.godot`, имя «Fixer», features 4.7.

**Что нужно сделать один раз:**

1. **Положить аддон внутрь проекта.** Godot грузит плагины только из `res://addons/`, то есть изнутри папки проекта, а аддон лежит рядом с ней. Без этого шага плагина в списке не будет:

   ```powershell
   New-Item -ItemType Directory -Force "F:\WORK\Fixer\game\addons" | Out-Null
   Copy-Item -Recurse "F:\WORK\Fixer\addons\godot_mcp" "F:\WORK\Fixer\game\addons\godot_mcp"
   ```

2. **Включить плагин.** Либо через UI: *Project → Project Settings → Plugins → «Godot MCP» → Enable*. Либо правкой `game/project.godot`:

   ```ini
   [editor_plugins]

   enabled=PackedStringArray("res://addons/godot_mcp/plugin.cfg")
   ```

3. **Запустить редактор с проектом:**

   ```powershell
   & "F:\WORK\Fixer\tools\Godot_v4.7.2\Godot_v4.7.2-stable_win64.exe" --path "F:\WORK\Fixer\game" --editor
   ```

4. **Проверить.** Внизу редактора появляется панель **MCP** с точкой статуса и логом команд. Со стороны агента — `godot_health_check` должен показать `bridge_connected: true`.

**Автозагрузчик для живых инструментов.** Редакторские инструменты (сцены, скрипты, свойства) работают сразу. Чтобы работали `play_scene`, ввод и play-тесты, нужен автозагрузчик: *Project Settings → Globals → Autoload* → добавить `res://addons/godot_mcp/mcp_runtime_probe.gd` под именем `MCPRuntimeProbe`. Скрипт сам ничего не делает вне debug-сессии, поэтому его безопасно держать включённым.

**Переменные окружения** (нужны редко): `GODOT_MCP_BRIDGE_URL` — если порт 9080 занят; `GODOT_MCP_BRIDGE_TOKEN` — общий токен, если мост слушает не только localhost. По умолчанию **ничего настраивать не нужно**.

**Наборы инструментов.** По умолчанию включены `core` и `inspection` (диагностика и чтение). Остальные — `scene_edit`, `scripts`, `runtime`, `project`, `composite` и прочие — включаются по мере надобности.

**Про `.gitignore`.** В `game/.gitignore` игнорируется только `.godot/`. Аддон **не** игнорируется: он часть тулчейна и должен быть в репозитории, иначе связка не воспроизводится на другой машине.

**Проверено 2026-09-26 (живыми вызовами, не по документации):**

- `godot_inspection_get_project_info` → проект `Fixer`, движок `4.7.2-stable (official)`, путь `F:/WORK/Fixer/game/`.
- `godot_debug_workflow` → `parse.ok = true`, **0 ошибок разбора** по всему проекту (включая 103 файла аддона).
- Аддон лежит в `game/addons/godot_mcp/`, плагин включён в `project.godot`, автозагрузка зарегистрирована.

**Две вещи, за которыми надо следить:**

1. **Имя автозагрузчика.** Зарегистрировано как `McpRuntimeProbe`, а сервер в своих подсказках называет его `MCPRuntimeProbe`. Регистр может оказаться значимым для проверки `required=runtime_probe` — это выяснится на первом же play-сеансе. Если живые инструменты откажут, первым делом переименовать автозагрузку в `MCPRuntimeProbe`.
2. **В проекте теперь два движка.** Редактор запускается из `tools/Godot_v4.7.2/`, а headless-прогоны сервер делает своим путём: `F:\WORK\Godot_v4.7.2-stable_win64.exe\...`. Сейчас версии совпадают, но это два независимых бинарника — при обновлении одного из них прогоны и редактор разъедутся. Проверять версию обоих при расхождениях в поведении.

**Побочный факт:** headless-прогон проекта без главной сцены не завершается сам (Godot открывает пустой цикл), поэтому выглядит как таймаут. Это не ошибка — лечится флагом `--quit-after <N>`.

**Про скиллы.** На машине есть общий скилл `godot-4-development` (`F:\WORK\.dsh\skills\`, 33 КБ, китайский, обзор возможностей Godot 4.x). **Решено не подключать его к проекту.** Причины: он не покрывает то, на чём стоит наша верификация (`--script`, коды возврата, тест-фреймворк, детерминизм, контент-данные), и предписывает каноничную раскладку `scenes/ scripts/ assets/`, которая спорит с выбранным разделением слоёв (§6, D14). Вместо него: `godot_describe_class` через MCP (метаданные **установленной** версии 4.7.2), `--help` у самого бинарника, официальные доки и этот документ. Обращаться к общему скиллу точечно, читая файл, — можно; в каталог сессии не ставить.

## 10. Открытые технические вопросы

1. ~~Точная версия Godot 4.x~~ — **решено:** 4.7.2 stable, `tools/Godot_v4.7.2/`.
2. Формат определения окна решения: единая схема для всех типов (сбой / подтверждение / импровизация) или разные. В П1 есть один вид окна (`locked_door`), вопрос станет живым со вторым.

4. Как хранить «память» героя (бесплатные устаревшие данные о местах, где он был) — как отдельный канал разведки или как модификатор существующих.

**Незакрытое из финального ревью П1** (оба — в тестах, продакшен верен):

5. **Защита красного пути несостоятельна.** `tests/run_red.gd` — отдельная копия логики раннера с жёстко зашитым кодом 1, поэтому зашитый `quit(0)` в `run.gd` он не поймает. Настоящая защита — общий модуль подсчёта для обоих входов, возвращающий 0, если нарочная ошибка не зафиксирована.
6. **Тест «подход к запертой двери со стороны b» покрытия не даёт.** Продакшен-дефект устранён (условие направления убрано из `_maybe_open_window`), но кейс стартует из `a`, поэтому с восстановленным старым условием остаётся зелёным. Нужен кейс, реально подходящий из `b`.

**Осознанно за бортом П1** (не дефекты, а границы этапа): загрузка миссии из JSON и валидатор контента; поиск пути (маршрут задаётся явным списком, после цели — прямой отрезок «цель → выход»); переключение на запасной маршрут при блокировке; направление взгляда и «заметил, но не понял»; интерфейс и карта.

# 01. Формат данных уровня

Это **единственный источник правды о форме**: поля, типы, обязательность, правила, коды ошибок.
Всё, что здесь написано, снято с работающего кода проверки и загрузки, а не с документации. Если
образец (`kit/example/mission.example.json`) и этот файл разойдутся — прав этот файл, и об этом надо
написать в отчёте.

**Что ты сдаёшь:** `mission.json` (данные уровня) и `texts.json` (все тексты по ключам).
Имена файлов произвольны, содержание — по этой спецификации.

---

## 0. Как читать эту спецификацию

Форма проходит **три уровня**, и они проверяют разное:

| Уровень | Что смотрит | Чем грозит |
|---|---|---|
| **Валидатор** | типы, обязательные поля, неизвестные поля, ссылки, законы уровня | список проблем с кодами; уровень **не собирается** вовсе |
| **Загрузчик** | превращает проверенный файл в модель уровня | не добавляет проверок: он работает только на уже проверенных данных |
| **Ядро операции** | читает модель в прогоне | молча игнорирует то, чего не понимает, — поэтому «эффект не из списка» проходит мимо игры |

**Главное следствие:** молчание ядра опаснее ошибки. Валидатор скажет `UNKNOWN_KEY` про лишнее
поле и `BAD_VALUE` про неизвестный эффект, но про эффект из списка, который ядро нигде не применяет
(таких сегодня нет: `engine_proposal` применяет только свой `fallback`), он не скажет ничего — и в
игре не произойдёт ничего. Ниже это названо в каждом месте.

**Правила записи, обязательные для всех:**

1. Числа — **целые**: пиши `4`, а не `4.0` и не `1.5`. **Дробное** значение (`1.5`) — ошибка формы
   (`WRONG_TYPE`), а не «округлится». Оговорка, снятая с кода: число с нулевой дробной частью
   (`4.0`) валидатор **пропускает** — он принимает и `int`, и целое значение с плавающей точкой
   (замер: `"steps": 1.0` в `kit/example/` → `ПРОБЛЕМ: 0`, а `"steps": 1.5` → `WRONG_TYPE
   edges[0].steps`). Пропуск — не разрешение: пиши целыми, как в примере.
2. JSON — строгий: без комментариев, висячих запятых и одинарных кавычек. UTF-8, отступ 2 пробела.
3. **`note` — строка — разрешён в любом объекте** и является единственным полем-пояснением. Он
   проверяется на тип (не строка — `WRONG_TYPE`) и больше ни на что не влияет.
4. **Никаких игровых фраз в данных.** В данных — только ключи (`*_key`), сами строки — в текстах.
5. **Поля, которого нет в этой спецификации, быть не должно.** Чего не хватает — оформляется
   заявкой движку `engine_proposal` (§7), а не своим полем.

**Что ядро читает из каждого раздела** (чтобы не было ожиданий, которых игра не выполнит):

| Раздел | Ядро читает | Раздел живой в игре? |
|---|---|---|
| `nodes` | id помещения (граф: рёбра, сенсоры, маршруты охраны, цель). `floor` доезжает до модели, но прогон его не читает; **теги читаются по имени**: `entry` — валидатором (по нему проверяется достижимость и маршруты), `shielded` — ядром (пока живой свой в таком помещении, эфира нет) | да |
| `edges` | `id`, `a`, `b`, `kind`, `steps`, `noise`, `locked` | да |
| `patrols` | `id`, `route`, `period` | да |
| `sensors` | `id`, `nodes` (зона видимости охраны) | да |
| `objective` | id помещения | да |
| `windows` | целиком (`trigger`, `options`, `silence`) | да |
| `routes` | **ничего в прогоне**: маршруты — норматив уровня, по ним считается «окон за прохождение» | **нет: замер приёмки** |
| `intel` | **ничего**: призраки охраны в ядре — это позиция охранника на старте прогона | **нет: экран и подсказки** |
| `floors`, `facility_key`, `pos`, `name_key` | **ничего**: это данные схемы | **нет: экран** |
| `texts` | ничего: тексты едут в модель и ждут экрана | **нет: экран** |

Последние строки — не «запрещено заполнять»: **наоборот, обязательно** (§12). Но в прогоне
они ничего не меняют, и рассчитывать на них как на механику нельзя.

## 1. Корень файла

```json
{
  "id": "mission-01",
  "title_key": "mission.01.title",
  "facility_key": "facility.meridian",
  "nodes": { "hall1": { "floor": 1, "tags": [], "pos": { "x": 0, "y": 4 }, "name_key": "room.hall1" } },
  "floors": { "1": { "name_key": "floor.1" } },
  "edges": [], "patrols": [], "sensors": [], "windows": [], "intel": [],
  "routes": [
    { "id": "r_main", "entry": "main_entry1", "exit": "main_entry1",
      "route": ["main_entry1", "reception1", "hall1", "archive0", "hall1", "reception1", "main_entry1"] }
  ],
  "objective": "archive0"
}
```

| Поле | Тип | Обязательность | Смысл |
|---|---|---|---|
| `id` | строка, непустая | **да** | id миссии. Пустая строка — `BAD_VALUE` |
| `title_key` | строка, непустая | **да** | ключ названия уровня (значение — в текстах) |
| `nodes` | объект, **непустой** | **да** | помещения; пустой объект — `EMPTY_SECTION` |
| `objective` | строка, непустая | **да** | id целевого помещения, обязан существовать |
| `edges` | массив | **да** (может быть пустым) | переходы и двери |
| `patrols` | массив | **да** (может быть пустым) | маршруты охраны |
| `sensors` | массив | **да** (может быть пустым) | зоны наблюдения |
| `windows` | массив | **да** (может быть пустым) | окна решений |
| `intel` | массив | **да** (может быть пустым) | данные разведки |
| `routes` | массив | **да** | объявленные маршруты: **ровно один на каждый вход** (§10) |
| `facility_key` | строка | нет | ключ названия комплекса |
| `floors` | объект | нет | подписи этажей: номер этажа → запись |
| `note` | строка | нет | пояснение для нас |

**Полный список разрешённых корневых полей — ровно этот.** Любое другое — `UNKNOWN_KEY`. В частности,
раздела **`access_points` в форме нет**: действие у терминала выражается вариантом окна (§5.5), а файл
с этим разделом валидатор отвергнет. Каждый из шести разделов-массивов **обязан присутствовать**, но
пустой массив — нормальная миссия: «поля нет» (`MISSING_FIELD`) и «поле есть, но не массив»
(`WRONG_TYPE`) — разные диагнозы. Единственное исключение — `routes`: он обязателен **и по смыслу**
(ровно один маршрут на каждый вход), и пустым быть не может, если входы объявлены.

### 1.1 `floors` — подписи этажей

Словарь: **ключ — номер этажа СТРОКОЙ** (`"-1"` для подвала: в JSON ключи объектов строковые),
значение — объект:

| Поле | Тип | Обязательность | Смысл |
|---|---|---|---|
| `name_key` | строка | **да** | ключ подписи этажа (`"floor.1"`) |
| `note` | строка | нет | пояснение |

Разрешённых полей ровно два (`name_key`, `note` — и всё). `floors` — **словарь, а не седьмой
раздел-массив**: `floors: []` даёт `WRONG_TYPE`.

**Чего `floors` не требует:** сверки с `nodes[].floor`. Запись этажа, на котором помещений нет, —
не ошибка; отсутствие записи для этажа, где помещения есть, — тоже не ошибка формы (но тогда на
схеме у этажа не будет подписи, см. §12).

## 2. `nodes` — помещения

Словарь: **ключ — id помещения**, значение — объект.

| Поле | Тип | Обязательность | Смысл |
|---|---|---|---|
| `floor` | целое | **да** | этаж: `-1` подвал, `0`–`5` этажи, `6` кровля. Отрицательные и любые другие — законны |
| `tags` | массив строк | нет | роли помещения; особые теги — `entry` (вход группы) и `shielded` (экранирование) |
| `pos` | объект | нет | координаты на схеме этажа: `{"x": целое, "y": целое}` |
| `name_key` | строка | нет | ключ подписи помещения (`"room.hall1"`) |
| `note` | строка | нет | пояснение |

**Рекомендуемые `tags`:** `entry` (вход), `shielded` (экранирование), `cold_archive`, `server`, `office`,
`stair`, `lift_main`, `lift_freight`, `roof`, `terminal`, `staff`. Список свободный — форма проверяет
только то, что это **массив строк**, и нового тега заводить не запрещает:
валидатор не знает закрытого перечня имён, потому что тег читается ядром **по имени**. Но два тега —
не пожелание, а механика:

- **`entry` делает помещение входом.** По нему работают проверки достижимости (§13), правило «ровно
  один маршрут на вход» (§10) и диагноз «окно на самом входе не сработает» (§5.2). Ни одного помещения
  с тегом `entry` — `UNREACHABLE` с сообщением «нет ни одного помещения с тегом entry — группу некуда
  ставить».
- **`shielded` — экранированное помещение.** Пока **живой** свой находится внутри, эфира нет вовсе:
  приказ не проходит (право голоса ложно), и окно решается молчанием. Игрок видит это как мёртвый
  эфир, а не как отказ игры. Зона **ничего не запрещает** и уровень не ломает: молчание не проваливает
  миссию, оно отбирает **авторство** там, где оно нужнее всего. Ставь `shielded` там, где по замыслу
  связи нет (подвал, экранированный зал), и помни: тексты и исходы молчания этих помещений обязаны
  читаться **без** приказа.

**`pos` — необязательное поле, но если оно есть, то обе оси обязательны.** Форма записи:

```json
"pos": { "x": 4, "y": 8 }
```

- разрешённые поля: `x`, `y`, `note` — и всё. Опечатка в имени оси (`"X"`) — `UNKNOWN_KEY`;
- отсутствие одной оси — `MISSING_FIELD` на своей оси; не целое — `WRONG_TYPE`;
- **отрицательные координаты законны**: схема может быть разложена и в отрицательную сторону.

**Почему координаты важны, хотя ядро их не читает.** По ним рисуется схема этажа на экране
операции. Считай, что каждое помещение занимает квадрат 3×3, и оставляй между помещениями одного
этажа зазор: в нашем рабочем уровне сетка имеет шаг 4, и это ровно «зазор 1 между коробками».
**Валидатор этого не проверяет** — наложение помещений он пропустит; это твоя ответственность, и
мы проверим это глазами и числами (§12).

**Почему `name_key` необязателен, а ставить его надо.** Без него помещение на схеме останется без
подписи. В нашем рабочем уровне `pos` и `name_key` есть **у каждого** помещения, и текст к каждой
подписи существует. Необязательность здесь — условие совместимости формы (уровень без координат
обязан грузиться), а не разрешение не рисовать карту.

**Чего валидатор у `nodes` не проверяет** (а надо соблюдать):
- id помещения непустой, латиница `[a-z0-9_]`;
- повтор ключа в объекте JSON **молча затрёт предыдущее помещение** — дубля быть не должно;
- уникальность id проверять нечем, потому что в объекте JSON дубли невозможны в принципе: остаётся
  последний. Проверяй глазами и сверкой числа помещений с задуманным.

## 3. `edges` — переходы и двери

| Поле | Тип | Обязательность | Смысл |
|---|---|---|---|
| `id` | строка | **да** | id ребра; уникален среди рёбер |
| `a`, `b` | строка | **да** | id помещений, оба обязаны существовать в `nodes` |
| `kind` | строка | **да** | вид связи, ровно из списка ниже |
| `steps` | целое ≥ 1 | **да** | цена перехода в шагах |
| `noise` | целое ≥ 0 | **да** | шум за переход |
| `locked` | логическое | нет (по умолчанию `false`) | заперто ли ребро **в начале** миссии |
| `note` | строка | нет | пояснение |

**Полный список `kind`** (других не бывает, и проверяются они ядром):

| `kind` | Смысл | Перекрывается ли тревогой |
|---|---|---|
| `door` | дверь | нет |
| `corridor` | коридор или проход | нет |
| `lift_main` | пассажирский лифт (Л1) | **да, сразу после тревоги** |
| `lift_freight` | грузовой лифт (Л2) | **да, через 3 шага после тревоги** |
| `stairs` | лестница | **никогда** |

**Запрещено** (каждое — свой диагноз):
- петля `a == b` — `BAD_VALUE` («ребро в себя»);
- **второе ребро между той же парой помещений** — `BAD_VALUE`: движок вернёт первое, второе
  останется невидимым навсегда. Если нужны две разные связи между одними помещениями (например,
  лифт и лестница) — заведи промежуточное помещение;
- `steps < 1` — `BAD_VALUE`; `noise < 0` — `BAD_VALUE`; `locked` не логическое — `WRONG_TYPE`;
- ссылка на несуществующее помещение — `BAD_REF` в поле `a` или `b`;
- неизвестный `kind` — `BAD_VALUE` со списком допустимых.

**Оговорка про пустой корпус.** Если `nodes` пуст (а это уже `EMPTY_SECTION`), ссылочные проверки
рёбер пропускаются: одна ошибка не должна порождать десяток следствий. Не полагайся на это — просто
не делай пустых `nodes`.

### 3.1 Что делает `steps` и `noise`

- `steps` — **не декорация**: агент тратит столько шагов на переход. На этом держится вся арифметика
  третьего акта (гонка после тревоги). Числа для ориентира — в `04-numbers.md`.
- `noise` — шум, добавляемый **при каждом проходе ребра**, любым агентом. Шум не затухает: это
  невозобновляемый бюджет.

### 3.2 «Запираемо» — ключевое понятие для окон

Ребро считается **запираемым**, если выполнено хотя бы одно:

1. в данных стоит `"locked": true`;
2. **его `kind` перекрывается тревогой** — то есть `lift_main` или `lift_freight`.

Окно с триггером `locked_edge` (§5.2) законно **только на запираемом ребре**. Окно на ребре
`door`/`corridor`/`stairs` с `locked: false` не сработает ни разу — и это дефект
`WINDOW_ON_OPEN_EDGE`. Окно на лифте, который закроет тревога, — **законно и правильно**: сцена
«застряли в лифте после тревоги» живёт именно так.

**Почему правило сформулировано через «вид перекрывается тревогой», а не «заперто сейчас»:**
валидатор работает с файлом и не знает состояния прогона — тревоги в файле нет. Вопрос ставится
правильно: «может ли это ребро вообще оказаться непроходимым».

## 4. Охрана: `patrols` и `sensors`

### 4.1 `patrols` — маршруты охраны

| Поле | Тип | Обязательность | Смысл |
|---|---|---|---|
| `id` | строка | **да** | id охранника; уникален среди патрулей |
| `route` | массив строк, ≥ 2 | **да** | маршрут по помещениям, **замкнутый**: последняя точка соединяется с первой |
| `period` | целое ≥ 1 | нет (по умолчанию 4) | через сколько шагов охранник делает следующий переход |
| `note` | строка | нет | пояснение |

**Запрещено:**
- id `kira` или `echo` — `RESERVED_ID`: эти id заняты своими агентами;
- повтор id патруля — `DUPLICATE_ID`;
- маршрут короче двух точек — `BAD_VALUE`;
- точка маршрута, которой нет в `nodes` — `BAD_REF`;
- **разрыв между соседними точками**: `route[k]` и `route[k+1]` обязаны быть соединены ребром —
  `BAD_VALUE` («разрыв маршрута»);
- **незамкнутый маршрут**: последняя точка обязана быть соединена ребром с первой —
  `PATROL_ROUTE_OPEN` (§16);
- `period < 1` — `BAD_VALUE`.

**Маршрут охраны — ЦИКЛ, и это условие работы ядра, а не украшение.** Охранник идёт по списку, а
**не по графу**: ядро берёт узлы по индексу и увеличивает индекс **по модулю длины списка**
(`route[0] → route[1] → … → route[n-1] → route[0]`). Поэтому замыкающая пара `route[n-1] →
route[0]` — такое же ребро маршрута, как соседние, и разрыв в ней называется **своим кодом**
`PATROL_ROUTE_OPEN` («маршрут не замкнут: «…» и «…» не соединены ребром, а охранник идёт по
кругу»).

**Почему разрыв запрещён, если рёбра охрана всё равно не смотрит.** Ядро у охраны рёбер **не
смотрит вовсе**: охранник не ходит по рёбрам и **на разрыве не застревает** — он просто
оказывается в помещении, которого не проходит, то есть **телепортируется** между несоединёнными
помещениями. Всё, что читает его позицию (сенсоры и окно `guard_in_sensor`, карта и «призраки»
разведки), видит патруль, прошедший сквозь стену. Правило нужно ровно за этим: список узлов и
топология уровня обязаны говорить одно и то же — маршрут охраны есть **цикл в графе**.

**Как это проверяется — обе половины цикла, и только они:**
1. каждая соседняя пара `route[k] → route[k+1]`: разрыв — `BAD_VALUE`;
2. замыкающая пара `route[n-1] → route[0]`: разрыв — `PATROL_ROUTE_OPEN`.

**Когда правило вообще применяется.** Замыкание судится **только о целом маршруте**: раздел `nodes`
не пуст, каждый узел маршрута существует, и каждая соседняя пара соединена ребром. Если в маршруте
уже есть разрыв между соседями или ссылка на несуществующее помещение, корень назван своим диагнозом
(`BAD_VALUE` или `BAD_REF`), и `PATROL_ROUTE_OPEN` **не выдаётся**: одна ошибка — одно следствие.
Тот же принцип у всего валидатора: проверки, зависящие от уже испорченного поля, пропускаются.

**Две формы в проверку замыкания не попадают, и обе — не разрыв:**
- маршрут из **двух** точек: соседняя пара и замыкающая — одна и та же, и о ней уже сказано
  `BAD_VALUE`; второго диагноза на один дефект не бывает;
- маршрут, **возвращающийся в первую точку** (`a, b, a`): перехода из точки в неё же нет (петли
  запрещены, §3), ядро проходит этот шаг как стояние на месте — замыкать нечего.

**Как убедиться, что правило живо.** В образце `kit/example/` все патрули — кольца из двух помещений
(`guard_1`: `reception1`, `hall1`), а у двухточечного кольца соседняя пара и замыкающая — одна и та же,
и о ней уже сказано выше. Возьми копию образца, допиши патрулю `guard_1` третью точку, соединённую
со второй, но **не** с первой (`"route": ["reception1", "hall1", "stair1"]`), и прогони комплект:
он назовёт `PATROL_ROUTE_OPEN` на `patrols[0].route` — «маршрут не замкнут: «stair1» и «reception1»
не соединены ребром, а охранник идёт по кругу» — и вернёт код 1. Готовый пример этой пробы — в
`kit/verifier/README.md` §5.

**Порядок элементов = порядок хода.** Патрули ходят в том порядке, в котором объявлены. Порядок
должен быть осмысленным (например, по этажам снизу вверх), а не случайным.

### 4.2 `sensors` — зоны наблюдения

Массив объектов: сенсор — зона, в которой охрана «видна» (камера, пост, датчик). Ядро читает ровно
`id` и `nodes`: вошедшая в зону охрана даёт событие контакта, а на него открывается окно с
триггером `guard_in_sensor` (§5.2).

| Поле | Тип | Обязательность | Смысл |
|---|---|---|---|
| `id` | строка | **да** | id сенсора; уникален среди сенсоров |
| `nodes` | массив строк, **непустой** | **да** | помещения зоны; каждое обязано существовать в `nodes` |
| `note` | строка | нет | пояснение |

**Проверяется:**
- `id` обязателен (`MISSING_FIELD` на `sensors[N].id`) и уникален — повтор даёт `DUPLICATE_ID`;
- `nodes` обязателен и обязан быть массивом (`MISSING_FIELD`, `WRONG_TYPE`); **пустой массив —
  `BAD_VALUE`** («сенсор без помещений бессмыслен»);
- помещение зоны, которого нет в `nodes` корня, — `BAD_REF` на `sensors[N].nodes` (ссылки
  проверяются, только когда корневой `nodes` непуст, — оговорка §3);
- лишнее поле — `UNKNOWN_KEY` (разрешены ровно три: `id`, `nodes`, `note`).

**Путь проблемы — по индексу, а не по id.** У сенсора своего имени в пути нет: `sensors[0].nodes`,
а не `sensors.s_lobby.nodes` — в отличие от рёбер, патрулей и окон, где id в путь попадает.

**Чего `sensors` не требует:** чтобы на сенсор ссылалось окно. `id` сенсора нужен только триггеру
`guard_in_sensor`, и форма о неиспользованном сенсоре молчит: сенсор без окна означает лишь
«здесь охрану видно», а не сцену для игрока. Осмысленность зон форма не проверяет — она на тебе.

**Но одно правило о сенсорах помнить обязательно.** Контакты сенсоров ядро выдаёт **только охране**:
зона «видит» вошедшего охранника и никого больше. Значит, сенсор — это **про охрану**, и сцена,
поставленная на `guard_in_sensor`, — тоже сцена про охрану. Если окно ссылается на сенсор, зону
которого **не посещает ни один патруль** (объединение маршрутов всех патрулей с зоной не
пересекается), окно не сработает никогда: `WINDOW_ON_UNVISITED_SENSOR` (§16). Чинится это двумя
разными правками — провести патруль через зону **или** переставить окно на `node_entered`, если
сцена вообще про человека, а не про охрану (§5.2).

## 5. `windows` — окна решений

**Окно — момент, когда группа упирается в ситуацию, которую игрок может решить приказом, а может
оставить именным.** Молчание встроено в форму окна.

```json
{
  "id": "w_archivist",
  "kind": "locked_edge",
  "trigger": { "type": "locked_edge", "edge": "e_hall0_archive0" },
  "text_key": "window.w_archivist.text",
  "options": [
    { "id": "bypass", "text_key": "window.w_archivist.bypass", "complexity": 2,
      "cost": { "noise": 0, "delay": 4 },
      "effects": [{ "type": "unlock", "edge": "e_hall0_archive0" }],
      "note": "только время: самый тихий путь" }
  ],
  "silence": {
    "text_key": "window.w_archivist.silence",
    "good_key": "window.w_archivist.silence.good",
    "neutral_key": "window.w_archivist.silence.neutral",
    "bad_key": "window.w_archivist.silence.bad",
    "safe_key": "window.w_archivist.silence.safe",
    "good": [{ "type": "unlock", "edge": "e_hall0_archive0" }],
    "neutral": [{ "type": "delay", "value": 2 }, { "type": "unlock", "edge": "e_hall0_archive0" }],
    "bad": [{ "type": "delay", "value": 2 }, { "type": "noise", "value": 5 },
            { "type": "unlock", "edge": "e_hall0_archive0" }],
    "safe": [{ "type": "delay", "value": 3 }, { "type": "unlock", "edge": "e_hall0_archive0" }]
  }
}
```

### 5.1 Поля окна

| Поле окна | Тип | Обязательность | Смысл |
|---|---|---|---|
| `id` | строка | **да** | id окна, уникален среди окон |
| `kind` | строка | **да** | вид окна; **обязан совпадать с `trigger.type`** |
| `trigger` | объект | **да** | когда окно открывается (§5.2) |
| `text_key` | строка | **да** | ключ текста ситуации |
| `options` | массив, ≥ 1 | **да** | варианты приказа (§5.3) |
| `silence` | объект | **да** | что происходит, если игрок молчит (§6) |
| `note` | строка | нет | пояснение |

**Вид окна и тип триггера — одно и то же значение, названное дважды.** Проверяемое совпадение:
`locked_edge`, `node_entered`, `guard_in_sensor`. Расхождение — `BAD_VALUE` («вид окна не совпадает
с триггером»). Причина: рантайм-вид ядро строит **из `trigger.type`**, а `kind` только повторяет
его для читателя, — несогласованный `kind` был бы полем-обманкой.

**Пустой `options` — `EMPTY_SECTION`; окно без `silence` — `MISSING_SILENCE`.**

### 5.2 `trigger` — три вида и только три

| `type` | Дополнительное поле | Когда срабатывает |
|---|---|---|
| `locked_edge` | `edge` — id ребра | группа **стоит перед непроходимым ребром** (замок или тревожная блокировка) и её следующий шаг — по этому ребру |
| `node_entered` | `node` — id помещения | группа **вошла** в помещение именно в этом шаге |
| `guard_in_sensor` | `sensor` — id сенсора | охрана **вошла** в зону сенсора именно в этом шаге |

Разрешённые поля триггера: `type`, `edge`, `node`, `sensor`, `note` — и всё. `type` обязателен и
обязан быть из списка (`BAD_VALUE` с перечнем). Якорное поле (`edge`/`node`/`sensor`) **обязательно
для своего вида** (`MISSING_FIELD`) и проверяется на существование объекта (`BAD_REF`).

#### Кто действует в сцене — правило, а не стиль

У окна ровно **три актёра**, и четвёртого способа «кто-то действует» в форме нет. Выбор актёра
диктует, какой триггер брать:

| Сцена про кого | Триггер | Почему |
|---|---|---|
| **группу** (вошла и увидела; человек в помещении; ситуация в комнате) | `node_entered` | сцену играет вход **группы**: событие приходит, когда группа входит в помещение |
| **охрану** (обход, дежурство, камера, в которую смотрит охранник) | `guard_in_sensor` | контакты сенсоров ядро выдаёт **только охране** |
| **запертую дверь** (группа упёрлась) | `locked_edge` | событие — подход группы к непроходимому ребру |

**Следствие, на котором спотыкались:** сцену «в помещении человек» (уборщица, свидетель, архивариус,
дежурный инженер) **нельзя** выразить через `guard_in_sensor` — там сцену играл бы охранник, а не
человек. Такая сцена ставится на `node_entered`. Обратно тоже верно: `guard_in_sensor` законен
**только** там, где патруль в зону сенсора действительно заходит.

**Три диагноза «окно не может сработать»** — все три форма называет сама, до приёмки:

| Код | Когда | Как чинить |
|---|---|---|
| `WINDOW_ON_ENTRY_NODE` | окно с `node_entered` стоит на помещении с тегом `entry` | группа там **стартует**, и события «вошла» не бывает: перенеси сцену на **первое помещение внутри**. Окно «на возврате» тоже не считается — к возврату миссия обычно уже завершена |
| `WINDOW_ON_UNVISITED_SENSOR` | окно с `guard_in_sensor` ссылается на сенсор, чью зону не посещает **ни один** патруль (объединение маршрутов) | проведи патруль через зону **или** переставь сцену на `node_entered`, если она про человека |
| `WINDOW_ON_UNREACHABLE_NODE` | якорь окна **группы** (помещение для `node_entered`, ребро для `locked_edge`) недостижим от объявленных входов по рёбрам. К окнам охраны это правило **не относится**: у `guard_in_sensor` актёр — охрана, а она **стартует** на своём маршруте и зону сенсора от входа не проходит, поэтому крыло, отрезанное от входов, для такого окна законно. За мёртвый сенсор отвечает своё правило — `WINDOW_ON_UNVISITED_SENSOR` выше | соедини якорь с графом: сцена группы в отрезанной части уровня не играется никогда |

**Других условий нет.** «Когда инженер выйдет из серверной», «когда игрок отдаст второй приказ»,
«когда тревога продержится пять шагов» — не выражаются. Берётся **ближайший** триггер из трёх, а
желаемое условие описывается заявкой движку (`engine_proposal` в эффектах, поле `needs`).

**Триггеры `node_entered` и `guard_in_sensor` смотрят только на СОБЫТИЕ ВХОДА текущего шага.**
«Группа находится в помещении давно» окном быть не может — иначе окно открывалось бы каждый шаг.
Для `guard_in_sensor` контакт снимается на входе в зону («не видно → видно»), и «охрана стоит в
зоне давно» окна не открывает.

**Одно окно срабатывает ОДИН РАЗ за миссию.** Повторных окон на одно ребро не бывает: ядро помнит
и сработавшее окно, и ребро, у которого окно уже сработало. Если нужно, чтобы событие случилось
дважды, — это заявка движку, а не второе окно.

**Окно выбирается по порядку массива:** окна перебираются в том порядке, в котором объявлены, и
срабатывает **первое** подходящее. Если два окна могут открыться в одном шаге — выиграет то, что
объявлено раньше. Порядок окон — часть замысла.

**Триггер `locked_edge` симметричен:** подход со стороны `b` упирается в дверь так же, как со
стороны `a`. Отдельного «окна для другой стороны» не нужно.

**Окно не открывается тому, кто в лифте уже поехал.** Тревожная блокировка держит только на
**старте** перехода (`progress == 0`): лифт, который уже поехал, назад не отзывают — иначе игрок
наказан за то, чего не мог предвидеть. Замок держит при любом `progress`.

### 5.3 `options[]` — варианты приказа

| Поле | Тип | Обязательность | Смысл |
|---|---|---|---|
| `id` | строка | **да** | id варианта, уникален **внутри окна**; `silence` запрещён |
| `text_key` | строка | **да** | ключ текста варианта — что игрок приказывает |
| `complexity` | целое 1–3 | **да** | сложность: сколько условий в приказе |
| `cost` | объект | **да** | цена варианта (§5.4) |
| `effects` | массив | **да** | последствия (§5.5); **пустой массив допустим** |
| `note` | строка | нет | пояснение |

**Запрещено:**
- вариант с `id` `"silence"` — `SILENCE_AS_OPTION`. Молчание встроено в форму окна и **приказа не
  тратит**; отдельного варианта у него быть не может;
- повтор `id` внутри окна — `DUPLICATE_ID`;
- `complexity` вне 1–3 — `BAD_VALUE`;
- **два варианта с одинаковой ценой и одинаковыми эффектами** — `DUPLICATE_ID` с сообщением
  «вариант совпал с … по цене и эффектам». Сравнивается сочетание `cost.noise` + `cost.delay` +
  последовательность эффектов. Выбор между такими вариантами ничего не меняет — это бессмыслица.

**Что такое `complexity` по смыслу.** Число условий в приказе: `1` — «выбить дверь»; `2` — «вскрыть
тихо, когда патруль уйдёт»; `3` — три условия и больше. Поле заполняется **честно**, а не «на глаз»:
если сложность **больше** Понимания исполнителя, приказ исполняется, но **буквально** — к его цене
детерминированно добавляется шум и задержка (числа — `04-numbers.md` §10), без кубика. То есть
дешёвый исполнитель предсказуемо дорог, а не «слаб по статам».

**Вариант должен различаться осмысленно:** цена (шум, задержка) против последствий. У каждого
препятствия нужен хотя бы один вариант, который **не тратит шум** (знание или время), и хотя бы
один, который **тратит шум, но экономит время**.

### 5.4 `cost` — цена варианта

| Поле | Тип | Обязательность | Смысл |
|---|---|---|---|
| `noise` | целое ≥ 0 | **да** | шум, который добавится сверх шума переходов |
| `delay` | целое ≥ 0 | **да** | задержка: на сколько шагов исполнитель встанет |
| `note` | строка | нет | пояснение |

Разрешённых полей ровно три. **`noise` и `delay` обязательны оба**, даже если одно из них ноль:
`{"noise": 0, "delay": 3}` — правильная запись; `{"delay": 3}` — `MISSING_FIELD` на `noise`.
Отрицательное значение — `BAD_VALUE`.

**Задержка адресная:** `delay` встаёт **тому агенту, чьё действие открыло окно**. Не всей группе.
Поэтому задержка «на 3 шага» — это не «группа стоит три шага», а «исполнитель отстаёт на три шага»,
и группа может разделиться.

### 5.5 `effects[]` — словарь эффектов, полный список

| `type` | Обязательные поля | Что делает ядро | Проверяется валидатором |
|---|---|---|---|
| `unlock` | `edge` (строка) | снимает **оба** запрета с названного ребра: замок `locked` и тревожную блокировку. Идёт по id, а не по виду: соседний лифт того же вида остаётся перекрытым | `edge` обязателен и обязан существовать (`BAD_REF`); у окна **не** с `locked_edge` — `BAD_VALUE` «открывать нечего». Проверяются **все** места окна, где бывают эффекты: `options[].effects`, четыре исхода `silence` и `fallback` заявки — см. ниже |
| `noise` | `value` (целое ≥ 0) | добавляет шум | `value` обязателен, не отрицательный |
| `delay` | `value` (целое ≥ 0) | задерживает исполнителя на `value` шагов | `value` обязателен, не отрицательный |
| `noop` | — | ничего. Нужен там, где важна только цена варианта | ничего сверх типа |
| `engine_proposal` | `id`, `want`, `needs`, `fallback` | **заявку не исполняет**: применяется только `fallback` (§7) | все четыре поля обязательны; `fallback` разбирается по тем же правилам, что эффекты |
| `money` | `value` (целое ≥ 0) | **копит** счётчик `money`: попадает в результат прогона | `value` обязателен, не отрицательный |
| `trace` | `value` (целое ≥ 0) | **копит** счётчик `trace`: попадает в результат прогона | `value` обязателен, не отрицательный |
| `mark` | `id` (**строка**) | ставит **именованную метку**: попадает в результат прогона (`marks`, по алфавиту, без повторов) | `id` обязателен и обязан быть строкой |

Разрешённые поля эффекта: `type`, `edge`, `value`, `id`, `want`, `needs`, `fallback`, `note`.
Лишнее поле — `UNKNOWN_KEY`. Неизвестный `type` — `BAD_VALUE` («для нового поведения нужен
engine_proposal»).

**Отдельно и явно: эффекта `reroute` НЕТ.** Он был в первой редакции постановки и снят: поиска пути
в ядре не существует, маршрут группы — явный список точек, и «перестроить маршрут через помещение»
выразить нечем. Если замыслу нужен уход группы в сторону, он выражается **парой `delay` +
`engine_proposal`** с `fallback` на этот `delay`: сегодня группа просто теряет время, а заявка
описывает, чем это должно стать. `reroute` в данных — `BAD_VALUE`.

**Правило «открывать нечего» стоит во ВСЕХ местах окна, где бывают эффекты.** `unlock` снимает
запрет с РЕБРА, а окна с триггером `node_entered` и `guard_in_sensor` срабатывают не на ребре:
`unlock` у такого окна открывает то, чего у окна в этот момент нет, и сцены у него не бывает.
Запрет — один код `BAD_VALUE` и одно правило на все места окна:

| Где объявлен эффект | Путь в диагнозе |
|---|---|
| вариант окна | `windows.<id>.options[N].effects` |
| исход молчания | `windows.<id>.silence.<качество>` |
| `fallback` заявки движку внутри варианта | `windows.<id>.options[N].effects[M].fallback` |
| `fallback` заявки движку внутри молчания | `windows.<id>.silence.<качество>[M].fallback` |

Ядро такой `unlock` всё равно исполнит — оно снимает блокировку по id ребра и о триггере не
спрашивает, — но полагаться на это нельзя: **держи `unlock` только в окнах с триггером
`locked_edge`**.

**Про `money`, `trace` и `mark` — читай внимательно: они исполняются.**
- `money` и `trace` — **счётчики**: копятся ядром за прохождение и попадают в результат прогона
  (`money`, `trace`). `value` обязателен и не может быть отрицательным.
- `mark` — **именованная метка**: выбор в окне ставит метку («взяли копию», «видели ответ»), метки
  идут в результат (`marks`, отсортированы по алфавиту) и питают финал. `id` — **строка**, и это
  не украшение: ось «копия против оригинала» выражается **выбором игрока** (меткой), а не перевозкой
  носителей. Число в `id` сделало бы выбор неразличимым в «Итогах», поэтому `id` — строка.

`money`/`trace`/`mark` **не требуют** `engine_proposal`: заявка нужна там, где просят **новое
поведение**, а не новый счётчик. Чего форма **не** знает — «сколько денег стоит победа»: трактовка
счётчиков (в том числе «след → осведомлённость») живёт на экране «Итогов», а не в данных уровня.
Клади эффекты честно по смыслу сцены и **перечисли в отчёте** (§3.3 шаблона), что именно они должны
означать в финале.

## 6. `silence` — молчание: четыре исхода по качествам

```json
"silence": {
  "text_key":    "window.w_archivist.silence",
  "good_key":    "window.w_archivist.silence.good",
  "neutral_key": "window.w_archivist.silence.neutral",
  "bad_key":     "window.w_archivist.silence.bad",
  "safe_key":    "window.w_archivist.silence.safe",
  "good":    [{ "type": "unlock", "edge": "e_hall0_archive0" }],
  "neutral": [{ "type": "delay", "value": 2 }, { "type": "unlock", "edge": "e_hall0_archive0" }],
  "bad":     [{ "type": "delay", "value": 2 }, { "type": "noise", "value": 5 },
              { "type": "unlock", "edge": "e_hall0_archive0" }],
  "safe":    [{ "type": "delay", "value": 3 }, { "type": "unlock", "edge": "e_hall0_archive0" }]
}
```

| Поле | Тип | Обязательность | Смысл |
|---|---|---|---|
| `text_key` | строка | **да** | базовый ключ текста молчания (запасной путь) |
| `good_key` | строка | нет | ключ текста исхода `good` |
| `neutral_key` | строка | нет | ключ текста исхода `neutral` |
| `bad_key` | строка | нет | ключ текста исхода `bad` |
| `safe_key` | строка | нет | ключ текста исхода `safe` |
| `good`, `neutral`, `bad`, `safe` | **массив** эффектов | **да, все четыре** | что происходит при этом качестве |
| `note` | строка | нет | пояснение |

**Четыре исхода — обязательны все.** Нет хотя бы одного — `MISSING_SILENCE`. Если исход есть, но
это **не массив** (одиночный объект) — `WRONG_TYPE`: одиночный объект допустим **только** у
`fallback` заявки движку. В `silence.<качество>` и в `options[].effects` — всегда массив,
даже из одного элемента.

**Поля `by` в форме нет.** Кто решает за игрока — определяет **состав группы в момент молчания**,
а не контент. Разные реплики под разные исходы — это ключи `…silence.good`, `…silence.bad` и т. д.

### 6.1 Кто решает и почему `safe` почти не выпадает

Качество исхода **выбирает ядро**, а контент описывает последствия. Правило ровно такое:

| Состав группы | Кто импровизирует | Возможные исходы | Как выбирается |
|---|---|---|---|
| есть **живой связист** (роль `comms`) | связист | `good`, `neutral`, `bad` | жребий: `good` — 50 %, `neutral` — 30 %, `bad` — 20 % |
| **связиста нет** (нет в составе или он выбыл) | тактик (`tactician`) | только `safe` | без жребия |
| нет ни связиста, ни тактика | никто | только `safe` | без жребия |

Жребий — единственный источник случайности во всей игре, и он живёт **в движке**, по seed прогона.
В контенте вероятностей нет и быть не может: ты описываешь все четыре последствия, а не выбираешь
качество.

**Следствие, которое обязан знать исполнитель: при штатном составе (тактик + связист) исход `safe`
не выпадает никогда.** Значит, **всё, что положено только в `safe`, на штатном составе не
сыграет**. Это не ошибка формы (проверка требует наличия всех четырёх исходов и не запрещает
`safe`), но `safe` — это ветка для составов **без связиста**. Если в `safe` лежит заявка движку,
которой нет больше нигде, — она мёртвая на штатном составе, и мы попросим назвать её в отчёте.
Пиши в `safe` «обход, дольше, но предсказуемо» и не клади туда единственную копию важного
эффекта — важное дублируй в `good`/`neutral`/`bad`.

**Молчание никогда не проваливает миссию.** Худшее, что делает `bad`, — тратит время, добавляет шум
и отдаёт инициативу. Ни один исход молчания не может убить, вызвать тревогу напрямую или сделать
уровень непроходимым.

### 6.2 Ключи текстов по качествам

`good_key`/`neutral_key`/`bad_key`/`safe_key` — **необязательные** поля: если ключа нет, игрок
увидит базовый `text_key`. Ставь их все четыре: иначе игрок увидит строку не того, кто решил.
Требование к ним одно, но жёсткое: **ключ качества обязан указывать на текст этого исхода** —
`bad_key` не может ссылаться на текст `…silence.good`. Формально валидатор сверит только наличие
ключа в текстах; смысловое соответствие проверим мы.

**Базовый `text_key` обязан быть верен при любом качестве** — он запасной. Поэтому в нём нельзя
называть решающего: при `good`/`neutral`/`bad` решает связист, при `safe` — тактик. Пиши без имени.

## 7. `engine_proposal` — как просить движок

Везде, где эффектов из §5.5 не хватает, ставится объект:

```json
{ "type": "engine_proposal",
  "id": "lure_engineer",
  "want": "Инженер выходит из серверной, дверь остаётся открытой 3 шага",
  "needs": "состояние охранника «вне поста» и таймер возврата",
  "fallback": { "type": "unlock", "edge": "e_liftmain2_server2" } }
```

| Поле | Обязательность | Смысл |
|---|---|---|
| `id` | **да** | короткое имя механики, латиницей; **уникально в пределах миссии** (уникальность ядро не проверяет — это на тебе) |
| `want` | **да** | что должно произойти, словами, одно-два предложения |
| `needs` | **да** | чего не хватает в движке |
| `fallback` | **да** | эффект, который сработает, **если заявку отклонят** |

**`fallback` — один эффект объектом ИЛИ массив эффектов; форматы равнозначны.** Это единственное
место, где одиночный объект допустим.

**Пустой `fallback` (пустой массив) — `BAD_VALUE`**, а не «верный тип»: тип как раз верный, пусто
содержимое, и сказать надо это. `fallback` не той формы (строка, число) — `WRONG_TYPE`.

**Без `fallback` артефакт не принимается.** Причина: если заявку отклонят, окно останется без
эффекта, и уровень перестанет работать. **`fallback` — это то, что делает уровень проходимым уже
сегодня.** Он разбирается по тем же правилам, что эффекты: `unlock` в `fallback` обязан открывать
существующее ребро, и именно он зачитывается в проверке выполнимости окна у двери (§8).

**Молчаливое расширение схемы своими полями — провал.**

## 8. Окно у двери: главное правило уровня

Окно с триггером `locked_edge` срабатывает **один раз**. Приказ может быть и не отдан. Поэтому:

> **Если окно стоит у запираемого ребра, хотя бы один из четырёх исходов молчания обязан
> открывать ИМЕННО это ребро.**

Иначе — `UNWINNABLE_EDGE`: группа останется перед дверью навсегда. В зачёт идёт `unlock` на это
ребро — **сам или внутри `fallback`** заявки движку; варианты в зачёт **не идут**: молчание не
должно означать провал.

**Проверка выполняется только для существующего ребра с честным `locked`:**
- ребра нет — уже сказано `BAD_REF`, второго следствия не будет;
- `locked` не логическое — уже сказано `WRONG_TYPE`, о запертости судить не по чему;
- ребро **не запираемо** — это отдельный диагноз `WINDOW_ON_OPEN_EDGE` («окно не сработает
  никогда»), а не невыполнимость;
- форма молчания неполна или неверна — уже сказано `MISSING_SILENCE`/`WRONG_TYPE`, о
  выполнимости судить рано.

**Почему валидатор требует один исход, а мы просим четыре.** В нашем рабочем уровне `unlock` стоит
во **всех четырёх** исходах окна у двери, и это правильно: тогда «молчание» при любом качестве
означает «дверь открыта, разной бывает только цена». Если `unlock` есть только в `good`, то при
`neutral`/`bad` группа платит временем и всё равно проходит; если его нет **нигде** — уровень
сломан. Требование формы — минимум; наша просьба — все четыре.

## 9. `intel` — данные разведки

```json
"intel": [
  { "channel": "agents", "observed_at": 0,
    "entries": [
      { "kind": "patrol", "id": "guard_3", "route": ["hall4", "it_open4", "hall4", "hall3"],
        "period": 6, "age_hours": 6, "false": true, "note_key": "intel.agents.patrol_false" },
      { "kind": "door_state", "node": "it4", "age_hours": 6, "false": false,
        "note_key": "intel.agents.server_closed" }
    ] }
]
```

В этом примере настоящий `guard_3` ходит `hall4 ↔ it_open4` с периодом 4, а призрак агентуры — другим
маршрутом **и** с другим периодом (6). Так и надо: расхождение обязано быть **в обоих** признаках —
совпадение любого из двух форма называет диагнозом `GHOST_SAME_AS_REAL` (§16).

| Поле блока | Тип | Обязательность | Смысл |
|---|---|---|---|
| `channel` | строка | **да** | канал: `drone`, `agents`, `hack` — значение **сверяется со списком** |
| `observed_at` | целое ≥ 0 | нет (по умолчанию 0) | шаг, на который сделан снимок |
| `entries` | массив | **да** | пункты данных; отсутствие или не-массив — `MISSING_FIELD` |
| `note` | строка | нет | пояснение |

| Поле пункта | Тип | Обязательность | Смысл |
|---|---|---|---|
| `kind` | строка | **да** | `patrol`, `sensor`, `guard_count`, `door_state` |
| `age_hours` | целое ≥ 0 | **да** | возраст данных в часах: источник расхождения «призрака» с реальностью |
| `id` | строка | для `kind: "patrol"` | id **существующего** патруля: ссылка проверяется (`BAD_REF`) |
| `route` | массив строк | — | маршрут призрака |
| `period` | целое | — | период обхода в призраке |
| `nodes` | массив строк | — | помещения (для `kind: "sensor"`) |
| `node` | строка | — | помещение (для `guard_count`, `door_state`) |
| `count` | целое | — | сколько охраны (`guard_count`) |
| `false` | логическое | — | **намеренно подброшено**: данные не совпадут с реальностью всегда |
| `note_key` | строка | — | ключ текста пояснения, который игрок увидит на карте |
| `note` | строка | — | пояснение |

**Проверяется:**
- `channel` обязателен (`MISSING_FIELD`), обязан быть строкой (`WRONG_TYPE`) и обязан быть
  **одним из трёх известных каналов** — `drone`, `agents`, `hack`. Иначе `BAD_VALUE` на своём
  поле: «неизвестный канал «…», допустимы: …»;
- `entries` обязателен и обязан быть массивом;
- `kind` обязателен и из списка (`BAD_VALUE` с перечнем);
- `age_hours` **обязателен** и не отрицательный;
- `observed_at` не отрицательный;
- `id` при `kind: "patrol"` обязан ссылаться на существующий патруль (`BAD_REF`);
- `route`/`nodes` — массивы **строк**; `period`/`count` — целые; `node`/`note_key` — строки;
  `false` — **строго логическое** (`WRONG_TYPE`);
- **у канала `agents` ровно ОДИН пункт с `"false": true`** — код `INTEL_LIE_COUNT` («подброшенных
  пунктов N, а у агентуры обязан быть ровно один»). Ноль и два — одинаково ошибка. Считаются только
  честные `true`; если хоть одна пометка `false` не логическая, счёт не ведётся вовсе (о ней уже
  сказано `WRONG_TYPE`);
- **призрак обязан расходиться с реальностью.** У каждого пункта вида `patrol` **маршрут И период**
  обязаны отличаться от реального патруля с тем же `id`. Диагноз `GHOST_SAME_AS_REAL` выписывается на
  **любое совпадение** — и на дословную копию (совпали и маршрут, и период), и на «совпал ровно один
  признак»: признак, который совпал, не расходится, а именно на расхождении стоит индикатор тревоги.
  Сообщение называет, **что именно** совпало (маршрут, период или оба) и каков реальный патруль, —
  правка у автора в этих случаях разная (развести путь или развести ритм). Правило смотрит только на
  существующий патруль (о несуществующем сказано `BAD_REF`) и только на читаемые поля (мусор в
  `route`/`period` назван своим `WRONG_TYPE`).

**Три известных канала — ровно эти, и пишутся дословно:**

| `channel` | Что даёт по смыслу |
|---|---|
| `drone` | кровля и верхние этажи |
| `agents` | расписания охраны; **единственный** канал, у которого правило лжи |
| `hack` | камеры и двери низа |

Перечень закрыт: канал адресует данные на экране и в текстах (`intel.<канал>.<пометка>`), поэтому
опечатка уносит блок из своего канала молча — данные приехали, а на экран не попали. Именно
поэтому значение сверяется, а не только тип.

**Каскад погашен: у неизвестного канала диагноз РОВНО один.** Правило «ровно один подброшенный
пункт» считается только по **известному** каналу `agents`; на `"agentss"` второго диагноза
(`INTEL_LIE_COUNT` про агентуру, которой в файле нет) не будет — это был бы второй диагноз одному
дефекту.

**Чего `intel` не проверяет:**
- **маршрут призрака с графом не сверяется.** Подброшенное расписание может называть помещение,
  которого в миссии нет или которое есть, но не на том этаже, — это замысел (ложь разведки), а не
  дефект ссылки;
- согласованность `age_hours`, `route`, `period` между каналами — на тебе.

**Почему расхождение — правило, а не пожелание.** Сцена «призрак разошёлся» — **единственный
индикатор тревоги** в игре: отдельной шкалы нет, и игрок читает опасность по тому, что карта
перестала совпадать с реальностью. Совпавший признак не расходится: маршрут без периода исчезает
через такт, а период без маршрута виден только по времени, — поэтому диагноз выписывается на
**любое** совпадение, а не только на полную копию. «Честный, но устаревший» пункт выражается
**возрастом данных** (`age_hours`), а не копией расписания.

**Ложь фиксирована, а не случайна.** Каждый канал врёт предсказуемо и одинаково при каждом прогоне:
больше одного подброшенного пункта у агентуры — ошибка, случайная ложь — ошибка. Игрок должен иметь
возможность выучить ложь и переиграть.

**Что видит ядро.** Сегодня `intel` не влияет на прогон: «призрак» охраны в ядре — это позиция
охранника на момент старта, и он расходится с реальностью сам, когда охрана идёт по расписанию.
`intel` — данные **экрана** (подписи «данные устарели на 7 ч», «НЕ СОВПАЛО»), и заполнять их надо:
именно они дают игроку право на осмысленный план.

## 10. `routes` — объявленные маршруты (норматив уровня)

```json
"routes": [
  { "id": "a_main", "entry": "main_entry1", "exit": "main_entry1",
    "route": ["main_entry1", "reception1", "hall1", "stair1", "stair2", "hall2", "kitchen2",
              "hall2", "stair2", "stair1", "hall0", "archive0", "hall0", "stair1", "hall1",
              "reception1", "main_entry1"],
    "note": "замысел прохождения от главного входа: подъём на 2-й, свидетель и кухня, затем спуск
             в подвал; назад тем же путём, каким вошёл" }
]
```

| Поле | Тип | Обязательность | Смысл |
|---|---|---|---|
| `id` | строка | **да** | id маршрута; уникален среди маршрутов |
| `entry` | строка | **да** | помещение с тегом `entry`, откуда маршрут начинается |
| `exit` | строка | **да** | помещение с тегом `entry`, куда маршрут приходит (в MVP — один из входов) |
| `route` | массив строк, непустой | **да** | список помещений по порядку прохождения |
| `note` | строка | нет | пояснение: чем этот замысел отличается от других |

**Правила — их пять, и каждое проверяет форма:**

1. **Ровно один маршрут на каждый узел с тегом `entry`**, и каждый такой узел обслужен ровно раз.
   Пропущенный вход — `ROUTES_PER_ENTRY` («нет маршрута для входа: …»); два маршрута с одним входом —
   тот же код («больше одного маршрута у входа: …»).
2. **`entry` и `exit` — узлы с тегом `entry`.** Существующее помещение без тега — `ROUTE_END_NOT_ENTRY`
   («это не вход» / «это не выход»); несуществующее — `BAD_REF`.
3. **`route[0]` совпадает с `entry`, последний элемент — с `exit`** — иначе `BAD_VALUE`
   («маршрут начинается с «…», а объявленный вход — «…»»).
4. **Каждая пара соседних помещений соединена ребром** — маршрут это прохождение по РЁБРАМ графа.
   Разрыв — `BAD_VALUE` («разрыв маршрута»).
5. **Цель лежит на маршруте** — `OBJECTIVE_OFF_ROUTE`. Иначе норматив считался бы по проходу, который
   к цели не ведёт.

**Зачем это в данных.** Норматив «8–9 срабатывающих окон за прохождение» мерится **на этих маршрутах**,
а не на догадках проверяющего о том, как ты задумал прохождение. Маршрут — это **замысел**, а не
перечень всего, что игрок может сделать: веди его через кандидата (2-й или 4-й этаж), зацепку и спуск
в подвал так, как уровень задуман. Неудобный маршрут не спрятать: число, от которого зависит вердикт,
берётся отсюда.

**Выход — один из входов.** «Уходишь тем путём, каким вошёл». Отдельного выхода форма не знает;
понадобится — это отдельное решение, а не молчаливое расширение.

**Автоматические маршруты проверяющего — не норматив.** Кроме объявленных, приёмка строит свои
(BFS «вход → цель» и «вход → якорь окна → цель») и отвечает ими на **другой** вопрос: способно ли
**каждое** объявленное окно сработать вообще, нет ли мёртвых окон. Числа этой выборки печатаются
отдельно и на норматив не влияют.

## 11. Тексты: сверка в обе стороны

Тексты — **плоский словарь** «ключ → строка», все строки уровня живут только там.

### 11.1 Обязательные системные ключи — 31, дословно

Они относятся к системе (переговоры, эфир, журнал, итоги, голоса), а не к конкретному окну. Их
отсутствие в текстах — `MISSING_REQUIRED_TEXT` с путём `texts.<ключ>`.

```
negotiation.intro
negotiation.term.money
negotiation.term.time
negotiation.term.truth
negotiation.mediator.recognize
negotiation.mediator.answer.press
negotiation.mediator.answer.yield
negotiation.dossier.offer
negotiation.dossier.read
negotiation.deal
team.kira.available
team.echo.available
team.market.intro
log.silence
log.command.kira
log.command.echo
log.command.you
log.radio.jammed
log.radio.intercepted
log.alarm.raised
log.ghost.mismatch
voice.kira.ack
voice.kira.command
voice.echo.joke
final.read
final.hand_over
final.destroy
outcome.extracted
outcome.caught
outcome.timeout
results.summary
```

**Названия миссии в этом списке НЕТ — и вот почему.** Название миссии держит **поле данных
`title_key`**, обычная сверка `*_key`: пропал текст — `MISSING_TEXT` на поле `title_key`. В списке
системных ключей его держать **нечем**: список не знает номера миссии, и жёсткое `mission.01.title`
внутри него выдавало бы ложную ошибку любой другой миссии. Так что заглавие уровня — **твоя
ответственность как обычного поля данных**: завёл `title_key` в данных — завёл текст к нему.
Ровно так же работают `room.*`, `floor.*`, `facility.*`, `window.*`, `intel.*`, `ap.*`.

**Список проверяется поштучно и не расширяется.** Нет ни «проверки непустоты блока»
(«в семействе `log.*` есть хотя бы один ключ»), ни обратного послабления: пропал один
обязательный ключ — назван **именно он**.

**И одно исключение, которое стоит знать.** Если обязательный ключ назван **данными** (каким-нибудь
полем `*_key`), пропажу называет не `MISSING_REQUIRED_TEXT`, а обычная сверка — `MISSING_TEXT` на
этом поле, и ровно один раз: ключ, на который данные ссылаются, второй раз не диагностируется. Ровно
так работает название уровня (§11.1 выше): `title_key` — поле данных, и его пропажу называет
`MISSING_TEXT` на `title_key`.

### 11.2 Сверка данных и текстов в обе стороны

1. **Каждый `*_key`, упомянутый в данных, обязан быть в текстах.** Иначе `MISSING_TEXT` с путём
   самого поля (`windows[0].silence.bad_key → ключа «…» нет в текстах`). Собираются
   **все** поля, чьё имя оканчивается на `_key`, на любой глубине: `title_key`, `facility_key`,
   `name_key` (помещения и этажи), `text_key` (окна, варианты, молчание),
   `good_key`/`neutral_key`/`bad_key`/`safe_key`, `note_key`.

   **Путь у `MISSING_TEXT` повторяет ФАЙЛ, а не разобранную форму.** Сверку ведёт обход сырых
   данных (`*_key` ищется прямо по словарям и массивам), и имени объекта ему взять неоткуда:
   по словарям путь идёт **по ключу** (`nodes.hall1.name_key`, `floors.1.name_key`), а по
   массивам — **по индексу** (`windows[0].silence.bad_key`, `routes[0].note`).
   Поэтому у окна это `windows[0].silence.bad_key`, а **не** `windows.w_archivist.silence.bad_key`.
   По id окна адресуют другие диагнозы — те, что идут по разобранной форме: `MISSING_FIELD`,
   `WRONG_TYPE` и правила окна называют поле `windows.<id окна>.<поле>`
   (`windows.w_archivist.text_key`). Одно и то же поле в выводе выглядит по-разному:
   `MISSING_TEXT windows[0].text_key` (текста нет) и `WRONG_TYPE windows.w_archivist.text_key`
   (поле не строка). Ищи **тот** путь, который назван: индекс — у `MISSING_TEXT`, имя окна — у
   диагнозов формы. Индекс `[0]` — позиция окна в массиве `windows` твоего файла.
2. **В текстах не должно быть лишних ключей** — тех, на которые данные не ссылаются. Это
   `DANGLING_TEXT`, и он ошибка, а не предупреждение.
3. **Исключение — служебные семейства.** Ключи, начинающиеся с `mission.`, `negotiation.`, `team.`,
   `log.`, `voice.`, `final.`, `outcome.`, `results.`, `intel.`, считаются законными, даже если
   данные на них не ссылаются: часть из них — обязательные системные (§11.1), часть адресуется по
   смыслу (пояснения разведки вида `intel.hack.patrol_false` собираются по каналу и пометке, а не по
   id пункта). Всё остальное (`room.*`, `floor.*`, `facility.*`, `window.*`, `ap.*`) обязано быть
   **выведено из данных** — иначе оно висячее.

**Практическое следствие:** не заводи «запасных» ключей окон и подписей, на которые никто не
ссылается. Каждый `room.*` обязан иметь `name_key` у соответствующего помещения, каждый `floor.*` —
запись в `floors`, каждый `window.*` — поле в окне.

**Про ключи качеств:** `*_key` качества — необязательные поля формы. Но если ты их завёл, текст
обязан быть, и он обязан быть текстом **этого** исхода.

### 11.3 Как проверить сверку самому

Комплект самопроверки (`kit/`) проверяет это первым делом, вместе с остальной формой. Отдельная
глазами проверяемая пара чисел: **число полей `*_key` в данных** (каждое поле — одна ссылка на
ключ; столько ключей обязано найтись в текстах) и **число ключей в словаре текстов**. Разница между
ними должна быть объяснима целиком: системные ключи, пояснения разведки, голоса и подписи.

В нашем рабочем примере `kit/example/` эти числа такие (замер, не глазомер):

| Число | Значение |
|---|---|
| полей `*_key` в данных (`mission.example.json`) | **163** |
| ключей в текстах (`texts.example.json`) | **209** |
| разница | 46 = 31 обязательный системный ключ (§11.1) + 15 ключей «по смыслу» (`voice.*` — 11, `final.partial_copy` и `final.reveal.*` — 4) |

Расхождение в любую сторону — это либо `MISSING_TEXT`, либо `DANGLING_TEXT`, и комплект назовёт его
поимённо. У **твоих** файлов числа будут другие: важно не «как в примере», а чтобы каждая разница
объяснялась перечнем ключей вне данных.

## 12. Что нужно уровню, чтобы его можно было нарисовать

Формально всё это необязательно, и валидатор промолчит. Но экран операции рисует схему **из
данных**, и без этих полей рисовать нечего:

1. **`pos` у каждого помещения** — координаты на сетке этажа, шаг 4, коробка 3×3, помещения одного
   этажа не наезжают;
2. **`name_key` у каждого помещения** и текст к нему (`room.<id>`);
3. **`floors` с `name_key` на каждый этаж, где есть помещения**, и тексты к ним;
4. **`facility_key` в корне** и текст к нему — название комплекса на схеме.

Валидатор проверит только **тип** этих полей; наложение коробок и сетку он не смотрит. Зато это
смотрит **наш инструмент приёмки**, и он краснеет именованным критерием: `pos` обязателен у каждого
помещения, расстояние между любыми двумя помещениями одного этажа — **не меньше 4** (коробка 3×3 на
шаге 4), у каждой подписи (`name_key`, `floors.*.name_key`, `facility_key`) обязан быть текст.
Поэтому в этой редакции постановки **топология, сданная без карты, вернётся на переделку** —
это требование задания (`00-task.md` §3 п. 8), а не пожелание.

## 13. Достижимость и проходимость: что проверяется, а что нет

**Проверяет валидатор** (до сборки миссии):
1. **вход → цель**: от **каждого** помещения с тегом `entry` до `objective` есть путь по рёбрам.
   Нет пути — `UNREACHABLE` «от входа «X» до цели «Y» нет пути», отдельное сообщение на каждый вход;
2. **цель → вход**: от `objective` достижим хотя бы один вход. Нет — `UNREACHABLE` «от цели «X» не
   дойти ни до одного входа»;
3. нет ни одного помещения с тегом `entry` — `UNREACHABLE` «группу некуда ставить»;
4. **объявленные маршруты** — пять правил §10, каждое своим диагнозом (`ROUTES_PER_ENTRY`,
   `ROUTE_END_NOT_ENTRY`, `OBJECTIVE_OFF_ROUTE`, `BAD_VALUE` на разрыв и несовпадение концов);
5. **якоря окон группы достижимы от входов**, и ни одно окно не стоит там, где сработать не может
   (`WINDOW_ON_ENTRY_NODE`, `WINDOW_ON_UNVISITED_SENSOR`, `WINDOW_ON_UNREACHABLE_NODE`, §5.2);
6. **призрак расходится с реальностью** у каждого пункта `patrol` (`GHOST_SAME_AS_REAL`, §9).

Обратный путь проверяется **явным обходом от цели**, а не выводом «граф неориентированный, значит то
же самое»: правило не должно зависеть от того, что рёбра сегодня проходимы в обе стороны.

**Чего валидатор не проверяет — и это твоя работа:**

1. **Два независимых пути к выходу.** Правило «от цели есть не меньше двух независимых путей к
   выходу» валидатор не знает. Проверяй сам: убери мысленно **все** перекрываемые тревогой рёбра
   (`lift_main`, `lift_freight`) — путь от цели к выходу обязан остаться. Иначе тревога превращает
   уровень в тупик.
2. **Тупики решений.** «Никаких тупиков, из которых не выйти ни одним решением» — вне формы.
   Ситуация «заперто, но есть обход дольше» — законная цена. «Заперто, и обхода нет» — дефект.
3. **Достижимость провала.** То, что при плохих решениях группа обязана попадать, — свойство
   прогона, а не файла.
4. **Целостность координат** (наложение помещений, попадание в сетку) — см. §12.
5. **Уникальность `id` заявок движку** и осмысленность их `needs`.
6. **Смысловое соответствие ключа качества его тексту** и то, что базовый текст не называет
   решающего (§6.2).
7. **Сколько окон срабатывает за прохождение** — это число считается прогоном, и считается оно
   **на твоих объявленных маршрутах** (норматив 8–9, §10).

Это не «дыры формы» — это проверки, которые делаются прогоном и глазами, и на приёмке мы делаем их
сами. Но лучше сделать их до сдачи.

## 15. Возврат из строя

Если валидатор нашёл хоть одну проблему, **миссия не собирается вовсе**: полумиссия в ядре хуже
отказа, потому что падает позже и непонятнее. Поэтому «одна проблема» — это «уровень не грузится»,
а не «почти всё хорошо».

**Порядок разбора проблемы:** код → путь → сообщение. `path` указывает место **в файле**
(`windows.w_archivist.silence.bad`, `nodes.hall1.pos.x`), по нему ошибка находится без чтения кода.

**Проверки, зависящие от уже испорченного поля, пропускаются:** одна ошибка в файле не должна
порождать десяток следствий, среди которых автор не найдёт причину. Поэтому список проблем может
быть коротким — и это нормально.

**Но не все следствия гасятся, и одно из них ты увидишь обязательно.** Поле-ключ (`text_key`,
`name_key`, `good_key`, `note_key`, `title_key`, `facility_key`), которого нет или
которое испорчено, оставляет свой текст **без ссылки** — и рядом с `MISSING_FIELD`/`WRONG_TYPE` на
этом поле приходит `DANGLING_TEXT` на его текст (замер: снятый `windows.w_lead_found.text_key` →
`MISSING_FIELD windows.w_lead_found.text_key` + `DANGLING_TEXT texts.window.w_lead_found.text`).
Это не вторая ошибка: чинить надо поле, а висячий ключ исчезнет сам.

## 16. Полный перечень кодов проблем

**Кодов ровно 26, и список полон:** валидатор не выдаёт кодов вне него. Колонка «Когда» — то, что
надо починить; `путь` в проблеме указывает место в **твоём файле**.

| Код | Когда |
|---|---|
| `MISSING_FIELD` | обязательного поля нет |
| `WRONG_TYPE` | поле есть, но другого типа (в сообщении — ожидаемое и полученное) |
| `UNKNOWN_KEY` | поля нет в схеме (в том числе целый раздел: `access_points` форма не знает) |
| `EMPTY_SECTION` | обязательный раздел пуст: `nodes`, `options` окна |
| `BAD_JSON` | файл не разбирается как JSON (путь `(корень)`, указывается строка) |
| `DUPLICATE_ID` | id повторяется внутри своего раздела; отдельно — «вариант совпал с … по цене и эффектам» |
| `RESERVED_ID` | id занят движком: `kira`, `echo` среди `patrols` |
| `BAD_VALUE` | значение вне допустимого (перечисление, диапазон, петля, второе ребро, разрыв маршрута **между соседними точками**, разрыв **маршрута патруля между соседними точками**, несовпадение концов объявленного маршрута, пустой список маршрута, неизвестный канал разведки, `unlock` у окна не про дверь) |
| `BAD_REF` | ссылка на несуществующий объект |
| `UNREACHABLE` | до цели нельзя дойти по рёбрам (в любую сторону) |
| `PATROL_ROUTE_OPEN` | **маршрут патруля не замкнут**: последняя точка не соединена ребром с первой. Маршрут охраны — цикл, и ядро водит охранника по кругу (индекс по модулю длины списка), поэтому разрыв в замыкающей паре означает, что охранник **телепортируется** между несоединёнными помещениями, а не идёт по уровню: его позиция врёт сенсорам, окну `guard_in_sensor` и карте. Сообщение называет **обе** точки замыкающей пары; в §4.1 сказано, какие две формы маршрута под это правило не попадают |
| `MISSING_SILENCE` | у окна нет молчания или в нём нет одного из четырёх исходов |
| `SILENCE_AS_OPTION` | «молчать» подсунуто обычным вариантом окна |
| `UNWINNABLE_EDGE` | ни один исход молчания не открывает ребро окна у двери |
| `WINDOW_ON_OPEN_EDGE` | окно ждёт запертое ребро, а оно не запирается ни замком, ни тревогой |
| `WINDOW_ON_ENTRY_NODE` | **окно входа стоит на самом входе**: группа там стартует, и события «вошла» не бывает. Перенеси сцену на первое помещение внутри (§5.2) |
| `WINDOW_ON_UNVISITED_SENSOR` | **зону сенсора не посещает ни один патруль**: контакты сенсоров ядро выдаёт только охране, и такое окно не сработает никогда. Проведи патруль через зону или переставь сцену на `node_entered` |
| `WINDOW_ON_UNREACHABLE_NODE` | **якорь окна ГРУППЫ недостижим от объявленных входов** по рёбрам: сцена группы в отрезанной части уровня не играется никогда. Сообщение называет, чем якорь является (помещение или ребро). Окна `guard_in_sensor` этим правилом не судятся: охрана стартует на своём маршруте и в зону от входа не приходит |
| `ROUTES_PER_ENTRY` | **на вход не ровно один объявленный маршрут**: «нет маршрута для входа: …» либо «больше одного маршрута у входа: …» |
| `ROUTE_END_NOT_ENTRY` | **`entry`/`exit` маршрута — не узел с тегом `entry`**: помещение есть, но это не вход (или не выход) |
| `OBJECTIVE_OFF_ROUTE` | **цель не лежит на объявленном маршруте**: проход, который к цели не ведёт, нормативом быть не может |
| `GHOST_SAME_AS_REAL` | **подброшенное расписание не расходится с реальным патрулём по обоим признакам**: совпал маршрут, период или и то и другое (сообщение называет, что именно): призрак не разойдётся с реальностью, и индикатор тревоги не работает |
| `MISSING_TEXT` | ключ текста из данных не найден в текстах |
| `MISSING_REQUIRED_TEXT` | обязательного системного ключа нет в текстах (путь `texts.<ключ>`) |
| `DANGLING_TEXT` | ключ текстов нигде не используется и не служебный |
| `INTEL_LIE_COUNT` | у канала `agents` подброшенных пунктов не ровно один |
